None은 문자열 'None'이 아니다. 커밋 ID가 아직 없다는 상태 값이다.

파일 끝의 __name__ 검사 때문에 import main만 할 때 REPL은 자동 실행되지 않는다.

validate_argument_count는 명령별 인자 개수를 검사한다. 공백이 있는 문자열도 따옴표로

옵션 이름·값은 명세의 표기를 따른다. 명령의 대소문자 무시와 옵션값 정규화는 다른 문제다.

D03: CI_0.parents=[]                main=CI_0, archive=None
D04: feature=CI_0 추가              head는 main 유지
D05: head='feature'                 커밋 데이터는 그대로
D06: CI_1.parents=['CI_0']          feature=CI_1, main=CI_0
D07: CI_2.parents=['CI_1']          feature=CI_2, main=CI_0
D08: head='main'                    현재 커밋은 CI_0
D09: CI_3.parents=['CI_0']          main=CI_3, feature=CI_2

CI_3을 만들 때 CI_2가 가장 최근에 생성됐더라도 부모는 CI_0이다.
create_commit은 저장소 전체의 마지막 커밋을 찾지 않고 branches[head]를 읽는다.

2. COMMIT 한 번의 처리 순서
① 초기화 여부를 확인한다.
② _generate_commit_hash()로 새 ID를 받는다.
③ branches[head]가 None이면 parents=[], ID이면 parents=[그 ID]로 만든다.
④ 현재 사용자·datetime.now()·메시지로 Commit 객체를 만든다.
⑤ store_commit으로 dict에 저장한다.
⑥ 현재 브랜치 위치를 새 ID로 바꾼다.
⑦ commit_index.add_commit으로 작성자·키워드 색인을 갱신한다.

명령이 성공해 반환됐을 때 커밋 저장소·브랜치 위치·두 역색인이 같은 새 ID를 참조한다.
이것은 코드의 호출 순서에 대한 설명이며, 별도 데이터베이스 트랜잭션을 구현했다는 뜻은 아니다.

3. BRANCH와 SWITCH는 무엇을 바꾸지 않는가
BRANCH: branches에 키와 현재 ID를 추가한다. Commit을 복제하지 않는다.
SWITCH: head의 브랜치 이름만 바꾼다. parents를 수정하지 않는다.
따라서 브랜치 전환 후 기존 커밋 author, timestamp, parents가 그대로다.

확인 질문: D04 직후 main과 feature가 같은 CI_0을 가리키면 커밋은 두 개인가?
답: 아니다. commits에는 하나이고, 두 브랜치 이름이 같은 ID를 가리킨다.

1. DAG의 세 단어
Directed: 부모를 읽는 기본 간선 방향은 자식 → 부모다.
Acyclic: 그 방향을 따라 계속 이동해 자기 자신으로 돌아오는 순환이 없다.
Graph: 커밋이 노드이고 parents의 연결이 간선이다.
분기, 여러 부모, 여러 루트가 있어도 DAG일 수 있다. DAG가 반드시 일자 이력인 것은 아니다.

2. 현재 생성 방식으로 순환이 생기지 않는 이유
새 ID는 기존 노드들과 다르다. 새 커밋이 참조하는 부모는 이미 존재하던 현재 커밋이다.
기존 노드의 parents는 변경하지 않으므로 기존 노드가 미래의 새 노드를 부모로 삼는
역방향 연결이 생기지 않는다. CLI 생성 과정에서 이 불변 조건을 유지한다.
검증용 객체를 임의로 훼손하는 모든 경우까지 사이클 검사를 하는 구현은 아니다.

3. 사이클의 문제
A의 부모가 B이고 B의 부모가 A이면, LOG에서 A가 B보다 먼저이면서 B도 A보다 먼저여야 한다.
이 조건은 만족시킬 수 없다. 방문 집합은 무한 반복을 막을 수 있지만 잘못된 이력을
올바른 DAG로 바꾸지는 않는다. 현재 Kahn 함수는 순환 입력을 별도로 검출해 오류를 내지 않는다.

4. ID 유일성과 dict 해시 충돌은 다르다
_generate_commit_hash는 CI_0, CI_1처럼 증가하는 번호를 사용한다.
후보가 commits에 있으면 카운터를 더 증가시켜 건너뛴다. store_commit도 동일 ID를 거부한다.
COMMIT 외에 가상의 SHA 해시 계산이나 파일 내용 해싱을 구현한 것은 아니다.

서로 다른 문자열이 dict 내부에서 충돌하는 일은 dict가 처리한다. 그것은 같은 커밋 ID를
두 객체에 부여하는 논리적 중복과 다르다. get_commit은 dict의 ID 키로 조회한다.
키 길이 등의 세부 비용을 별도로 두면 평균 조회 O(1)이다. 항상 최악 O(1)이라는 뜻은 아니다.

확인 질문: 커밋 ID의 숫자 크기로 PATH 동률을 비교해도 되는가?
답: 안 된다. 명세는 전체 문자열의 사전순이다. 예를 들어 CI_10은 CI_2보다 사전순에서 앞선다.

값은 전체 조상 수가 아니라 아직 처리되지 않은 직접 부모의 수다.

처리 전 ready     꺼낸 ID   처리 후 ready    결과
[CI_0]            CI_0      [CI_1, CI_3]     [CI_0]
[CI_1, CI_3]      CI_3      [CI_1]           [CI_0, CI_3]

ready.pop()이 끝에서 꺼낸다는 사실만으로 전체 알고리즘을 DFS라고 부르면 안 된다.
핵심 규칙은 남은 부모 수가 0인 노드만 고르는 Kahn 위상 정렬이다.

4. 비용과 출력
children 구성, 부모 수 구성, 노드·간선 처리를 합쳐 O(V+E)다.

================================================================

평가 연결: 1-4, 1-5, 3-3
코드 확인:

1. 두 탐색의 목적부터 구분
PATH: 부모 연결을 무방향으로 보고 최소 간선 수의 실제 경로를 찾는다.
ANCESTORS: 부모 방향으로 도달 가능한 모든 조상 ID를 수집한다.
같은 부모 데이터로 서로 다른 질문을 푸는 것이므로 이동 방향도 다르다.

2. D11의 도착점 기준 거리 표
요청: PATH CI_2 CI_3
build_distance_map(commits, 'CI_3')의 BFS 발견 순서와 거리:
  CI_3:0 → CI_0:1 → CI_1:2 → CI_2:3

컨테이너: dict[str, int]
키 'CI_2'는 ID, 값 3은 목표 CI_3까지 남은 최소 간선 수다.
현재 무방향 그래프에서는 목표에서 출발점까지와 출발점에서 목표까지의 거리가 같다.
waiting은 대기 ID 목록이며 read_position이 다음으로 처리할 인덱스다.
앞 항목을 pop(0)으로 삭제하지 않고 인덱스를 증가시켜 이동 비용을 피한다.

3. BFS가 최단 거리를 보장하는 이유
거리 0인 목표를 먼저 처리하고, 여기서 처음 발견한 이웃의 거리는 1이다.
거리 1인 노드들이 거리 2인 노드들보다 먼저 처리된다. 모든 간선 비용이 1이므로
처음 발견한 거리보다 짧은 경로가 뒤에서 나타날 수 없다. distance 포함 여부로 재방문을 막는다.
BFS는 방향 그래프에서도 쓸 수 있다. 무방향인 이유는 BFS의 한계가 아니라 과제 명세다.

4. 경로와 조상 결과
거리 감소 경로: CI_2(3) → CI_1(2) → CI_0(1) → CI_3(0).
최단 경로가 여러 개면 P10의 전체 문자열 비교가 추가로 필요하다.

ANCESTORS CI_2:
  발견·대기 시작: {'CI_1'}, ['CI_1']
  CI_1의 부모 CI_0을 발견: {'CI_1','CI_0'}, ['CI_0']
  CI_0에는 부모 없음 → 종료
알고리즘은 집합을 반환한다. CLI는 저장소 순서대로 조상만 골라 CI_0, CI_1을 출력한다.
알고리즘의 방문 순서와 화면 순서를 혼동하지 않는다. 시작점 자신은 초기 집합에 넣지 않는다.

================================================================

평가 연결: 1-6, 2-3, 3-5

1. 역색인을 바깥 → 키 → 값으로 읽기
keyword_index: dict[str, set[str]]
  키 'login': 정규화한 토큰 문자열
  값 {'CI_1','CI_2'}: 그 토큰이 있는 커밋의 ID 집합

원래 커밋 메시지는 바꾸지 않고 색인의 키만 lower().split()으로 만든다.

2. AND 검색 값 추적
query='login feature' → tokens=['login','feature']
login   → {CI_1, CI_2}
feature → {CI_1, CI_3}
교집합  → {CI_1}

find_by_keyword가 내부 set을 그대로 반환할 수 있으므로 첫 결과를 set(...)으로 복사한다.
그 뒤 교집합을 계산해도 원래 login 색인에 있던 CI_2는 사라지지 않는다.
SEARCH log는 login에 일치하지 않는다. 구문 순서도 검사하지 않으므로
'feature login'과 'login feature'는 같은 AND 조건이다. 이는 CHECK D1·D2의 선택이다.

3. 후보 ID에서 출력까지
CommitIndex → set[str]
Repository.search_by_keywords/search_by_author → ID로 조회한 list[Commit]
main.execute_command → 각 객체의 hash로 list[str]
format_log → 문자열
현재 main.py는 불필요한 리스트 중복 검사를 제거했다. 결과 ID를 한 번씩 모은다.
이 설명은 수정된 현재 코드 기준이며, 이전 O(k²) 중복 검사 비용을 여기에 붙이지 않는다.

4. 복잡도는 범위를 밝혀 말하기
단일 토큰·작성자: 해시맵의 평균 키 조회 O(1) + k개 조회·나열 O(k).
전체 메시지 길이·키 길이·출력 문자 길이를 별도로 두면 평균 O(1+k)다.
모든 커밋이 결과라면 k=V이므로 최소한 V개를 출력할 비용은 남는다.
여러 토큰은 각 후보 집합의 교집합 비용이 추가된다. 최종 결과가 적다고 중간 집합 비용도
항상 작은 것은 아니다. 커밋을 추가할 때 토큰 추출·색인 등록 시간과 저장 공간도 필요하다.

확인 질문: 작성자 이름을 자동으로 lower 해야 하는가?
답: 현재 정책은 정확한 일치다. 명령 대소문자 무시와 인자 내용은 구분한다.

[P10] 여러 부모와 최단 경로 동률
================================================================
대응 대본: script.txt [P10]
시연: B01~B03 / 이미지: Docs/Images/07_path_tie.png
평가 연결: 1-3, 1-4, 1-5
코드 확인:
  graph.py:86 find_shortest_path()
  graph.py:7 find_ancestors()
  graph.py:148 topological_order()

1. 검증용 DAG를 읽기
commits는 dict[str, Commit], 각 Commit.parents는 list[str]다.
h0:[] / h1:[h0] / h2:[h0] / h3:[h1,h2] / hx:[]
이 구조는 CHECK 12단계에서 제시한 직접 검증용 데이터다.
부모를 0개 이상 표현한다는 요구를 확인하는 것이지 merge CLI 시연이 아니다.

2. h0에서 h3까지의 최단 경로 동률
도착점 h3에서 무방향 BFS:
  distance={'h3':0, 'h1':1, 'h2':1, 'h0':2}
  hx는 연결되지 않아 표에 없다.

처리 순서와 best_suffix: dict[str, str]
  h3 → 'h3'
  h1 → 'h1->h3'
  h2 → 'h2->h3'
  h0의 후보 1 → 'h0->h1->h3'
  h0의 후보 2 → 'h0->h2->h3'
  비교 결과 h1 경유 선택

next_step: dict[str, str]는 선택한 바로 다음 ID를 저장한다.
  next_step['h0']='h1', next_step['h1']='h3'
이 표를 출발점에서 따라가 ['h0','h1','h3']을 복원한다.

3. 거리와 사전순의 우선순위
우선 간선 수를 최소화한다. distance가 1 줄어드는 이웃만 남기면 최단 길이를 벗어나지 않는다.
그 후보들에서만 전체 문자열을 비교한다. 사전순이 더 작아도 더 긴 경로는 선택하지 않는다.
BFS로 먼저 발견한 경로 하나를 그대로 쓰면 이웃 나열 순서에 따라 동률 규칙을 놓칠 수 있다.
개별 ID의 숫자 크기나, ID 목록의 비교를 전체 문자열 비교와 같다고 가정하지 않는다.

4. 왜 부모의 suffix가 먼저 준비되는가
distance dict는 BFS 발견 순서대로 들어간다. Python 3.10 이상 dict는 삽입 순서를 유지한다.
거리 0, 1, 2 순으로 처리하므로 현재 거리보다 1 작은 이웃의 suffix는 이미 준비되어 있다.
순서를 보장하는 이유는 dict 자체가 거리를 정렬해서가 아니라, BFS가 그 순서로 삽입했기 때문이다.

5. 여러 부모에서의 다른 함수
ANCESTORS h3은 h1/h2에서 같은 h0을 만나도 set으로 중복을 피한다.
LOG는 h3의 남은 부모 수가 처음 2이므로 두 부모를 모두 출력해야 h3을 처리한다.
현재 B03의 hx 첫 출력은 ready 끝에서 꺼낸 구현 결과이며, 명세상 고정 순서는 아니다.

확인 질문: next_step만 있으면 왜 best_suffix도 필요한가?
답: next_step은 복원용이다. 어느 다음 노드가 전체 문자열 기준 최선인지 비교할 정보는
best_suffix가 제공한다. 두 딕셔너리의 책임이 다르다.

[P11] 삽입 정렬과 안정성
================================================================
대응 대본: script.txt [P11]
시연: B04~B06 / 이미지: Docs/Images/06_insertion_sort.png
평가 연결: 1-6, 3-4, 3-5
코드 확인:
  sorting.py:6 get_sort_key()
  sorting.py:15 insertion_sort()
  index.py:25 CommitIndex.find_by_author()

1. 비교 기준과 알고리즘을 분리
get_sort_key(commit,'date')는 datetime인 timestamp를 반환한다.
get_sort_key(commit,'author')는 문자열 author를 반환한다.
삽입 정렬의 반복 구조는 같고 비교하는 값만 달라진다.
문자열 오름차순은 Python 문자열 비교 기준이며, 별도 한국어 사전식 정렬을 구현한 것은 아니다.

2. 작성자 삽입 정렬의 단계 (입력 h0,h1,h2,h3,hx)
처리 전: h0 Zoe | h1 Alice | h2 Bob | h3 Alice | hx Evan
h1 삽입: h1 Alice | h0 Zoe | h2 Bob | h3 Alice | hx Evan
h2 삽입: h1 Alice | h2 Bob | h0 Zoe | h3 Alice | hx Evan
h3 삽입: h1 Alice | h3 Alice | h2 Bob | h0 Zoe | hx Evan
hx 삽입: h1 Alice | h3 Alice | h2 Bob | hx Evan | h0 Zoe

바깥 반복의 i는 이번에 정렬된 앞 구간에 넣을 원소 위치다.
tmp_commit과 tmp_value로 현재 객체와 키를 잡아 두고 j=i-1부터 왼쪽을 검사한다.
더 큰 값을 오른쪽으로 옮기며 j를 줄인다. 끝나면 result[j+1]에 tmp_commit을 넣는다.
중간 목록에 동일 객체가 두 번 보이는 것은 이동 중의 임시 상태일 수 있다.
현재 원소를 tmp_commit에 보관했으므로 마지막 자리에 넣으면 누락을 피한다.

3. 안정성의 핵심은 >
현재 조건은 get_sort_key(result[j],sort_by) > tmp_value다.
h3(Alice)를 넣을 때 h1(Alice)는 더 크지 않으므로 이동하지 않는다.
따라서 h1이 h3보다 먼저였던 순서가 유지된다. >=로 바꾸면 같은 키를 추월할 수 있다.
안정 정렬은 같은 키끼리의 상대 순서에 대한 성질이며, 부모 관계를 보장하는 성질은 아니다.

4. 시간·공간 비용
평균(무작위 순서 가정)과 최악: 앞의 많은 원소를 이동 → O(n²).
역순 입력 이동량은 대략 1+2+...+(n-1)이다.
최선(이미 정렬): 각 i에서 비교가 바로 끝나므로 O(n).
복사 목록 공간: O(n). 비교하는 문자열 길이 등의 비용은 별도로 둔 분석이다.

5. B06의 의미
author_index['Alice']는 {h1,h3}. 다른 세 작성자의 ID는 포함하지 않는다.
준비할 때 add_commit을 호출했고, 검색은 그 연결을 직접 조회한다.
B04의 정렬 순서와 B06 집합의 출력 순서는 별개다.

확인 질문: 같은 날짜끼리도 안정적인가?
답: 그렇다. 선택한 키가 같을 때 이동하지 않는 조건이 두 기준에 공통 적용된다.

[P12] 성능과 부모 방향 PATH 가정
================================================================
대응 대본: script.txt [P12]
시연: 없음 / 이미지: Docs/Images/08_direction_and_constraints.png

1. 성장 비용은 변수부터 정하기
V=전체 커밋 수, E=부모 연결 수, k=검색 결과 수,
Vr=도달한 조상 탐색 영역의 노드 수, Er=그 영역의 부모 연결 수,
L=후보 경로 문자열의 최대 문자 수다.

조건: 커밋당 부모 수와 메시지 길이가 비슷하게 유지된다고 가정한다.
- dict 키로 한 커밋 조회: 평균 O(1). 커밋 수가 10배여도 조회 횟수 자체가 10배는 아니다.
- 기본 LOG: O(V+E). E도 같은 비율로 늘면 대략 10배.
- 삽입 정렬 평균/최악 O(V²): 대략 100배. 직접 구현한 병합 정렬 등으로 개선 가능하다.
- 단일 키 검색: O(1+k). 전체 결과가 필요하면 결과 수만큼의 출력은 남는다.

2. 지금 코드에서 빠뜨리기 쉬운 비용
find_ancestors는 list.pop(0)을 쓰므로 넓은 대기 목록에서 앞으로 옮기는 비용이 누적된다.
일반적인 중복 없는 부모 관계에서 최악 O(Vr²+Er)까지 커질 수 있다.
필수 CLI 이력은 한 커밋의 부모가 하나라 큐 폭이 작다. 여러 부모 검증에서 차이를 생각한다.
스택 pop()이나 읽기 인덱스로 개선할 수 있다. CLI의 조상 출력은 전체 저장소를 한 번
순회하므로 별도의 O(V) 비용도 있다.

PATH의 BFS 자체는 O(V+E)지만, best_suffix 전체 문자열을 각 노드마다 만든다.
거친 상한으로 계산 O((V+E)L), 문자열 저장 O(VL)을 고려한다.
먼저 필요한 거리 범위 밖의 suffix 생성을 줄일 수 있지만, 긴 경로 자체의 중복 저장 비용은
별개다. 문자열을 저장하지 않는 다른 표현으로 바꿀 때도 전체 문자열 동률 규칙을 유지해야 한다.
이 설명은 성능 비교 보너스를 구현했다는 뜻이 아니다. 현재 코드의 비용을 분석하는 답변이다.

3. 평가 4-2: 실제 이동 방향과 거리 계산 방향
B의 부모가 A이고 요청이 PATH B A라고 하자.
부모만 이동하도록 바꾸면 정답은 B→A이고, 반대 A→B는 경로가 없다.
현재 함수는 도착점 A에서 BFS를 실행한다. A의 부모만 읽으면 B를 발견할 수 없다.
따라서 현재 구조를 유지한다면 도착점에서 실제 간선을 뒤집은 자식 방향으로 BFS해야 한다.

  실제 허용 이동: B → A (부모 방향)
  거리 계산:      A → B (자식 방향, 역방향 BFS)
  거리 표: {'A':0, 'B':1}
  경로 선택: B의 부모 A를 골라 거리 1→0으로 이동

build_neighbors_map은 거리 계산과 경로 후보에서 모두 사용된다. 이 함수만 일괄 부모 목록으로
바꾸면 두 역할이 함께 바뀌므로 안 된다. 거리 계산용 관계와 실제 후보 관계를 분리한다.

4. 거리 표에 없는 부모도 주의
P,Q는 각각 부모 없는 루트이고 M.parents=[P,Q]라고 하자.
목표 P에서 자식 BFS: {'P':0,'M':1}. M의 다른 부모 Q는 목표 P로 갈 수 없다.
따라서 먼저 parent_id in distance인지 확인하고, 그 다음 거리가 1 줄어드는지 검사한다.
이를 생략하면 Q의 거리를 읽다가 KeyError가 날 수 있다.

확인 질문: 방향 그래프로 바뀌었으니 BFS를 DFS로 바꾸어야 하는가?
답: 아니다. 간선 비용이 모두 1이므로 BFS를 계속 쓸 수 있다. 바꿀 것은 이동 관계와
목표 거리의 계산 방식이다. 자세한 보충은 Graph_Study.md 17.2절을 참고한다.

1. 평가 4-3은 동시에 만족 가능한지부터 검토
부모 P의 author='Zoe', 자식 C의 author='Alice'이면:
  작성자 전체 오름차순: C → P
  부모 우선: P → C
둘을 무조건 동시에 만족시키는 순서는 없다. 어떤 조건을 우선할지 정의해야 한다.

부모 우선을 택하면 Kahn 방식의 ready 안에서만 작성자 기준으로 선택한다.
① 남은 부모 수 0인 후보를 준비한다.
② 후보 사이에서 작성자 값이 가장 작은 노드를 고른다.
③ 그 노드를 출력하고 자식의 부모 수를 감소시킨다.
④ 새로 0이 된 자식을 ready에 추가한다.

이 결과가 전역 작성자 오름차순을 보장하는 것은 아니다. 부모 조건을 만족하는 후보들 사이의
우선순위다. 위상 정렬 후 결과 전체를 작성자로 다시 정렬하면 부모 조건을 깨뜨릴 수 있다.
안정 정렬도 서로 다른 작성자의 부모·자식 충돌을 해결하지 않는다.
구현한다면 후보를 직접 최소 탐색하거나 우선순위 큐를 직접 구현하는 방안을 검토할 수 있다.
표준 정렬 API 금지는 계속 적용된다. 현재 이런 조건 변경 기능을 구현한 것은 아니다.

2. 평가 4-4: 카운터와 난수
카운터: 같은 초기 상태와 생성 순서에서 같은 ID를 얻기 쉬워 테스트의 기대값과 디버깅이 쉽다.
카운터 상태를 재사용하지 않고 기존 ID 확인을 해야 유일성을 설명할 수 있다.
난수: 실행마다 ID가 달라질 수 있다. 충돌 가능성이 작아도 중복이 없다는 보장은 아니다.
기존 ID 확인과 재생성 등 대응이 필요하다. 테스트에서 일부러 같은 후보를 공급해 확인할 수 있다.
seed: 의사난수 수열의 재현에 도움을 주며, 중복 금지 자체를 보장하는 장치는 아니다.

경로 동률도 실제 ID 문자열로 비교하므로, 같은 모양의 그래프라도 ID가 바뀌면 선택되는
경로가 달라질 수 있다. 이는 최단 거리와 문자열 규칙을 지켰다면 오류가 아니다.
