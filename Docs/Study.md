## 2. 학습 범위와 제약

**근거: Subject.txt 2장, 6장, 7장**

- Python 3.10 이상에서 동작하는 CLI 프로그램을 만든다. 엔트리 포인트와 `README.md`가 필수 제출물이다.
- 다루는 데이터는 커밋의 메타데이터다. 파일 내용 추적과 네트워크 통신은 구현 범위에서 제외된다.
- 메모리에서 동작하면 충분하다. 데이터를 파일에 저장하고 다음 실행에서 복구하는 기능은 필수가 아니다.
- 그래프 전용 라이브러리와 정렬 관련 표준 API를 사용할 수 없다. `sorted()`와 `list.sort()`도 금지된다.
- 탐색·정렬·인덱싱 로직은 독립된 함수 또는 클래스로 분리하고, 주요 함수·클래스에는 주석 또는 docstring을 작성한다.

소개에 등장하는 rebase와 cherry-pick은 구현 요구사항이 아니다. 실제 Git의 모든 동작을 재현하는 것이 이 과제의 완료 기준은 아니다.

## 3. 커밋, 브랜치, HEAD

**근거: Subject.txt 4장 「커밋 그래프」 및 `INIT`·`BRANCH`·`SWITCH`·`COMMIT`**

### 커밋은 어떤 정보를 가진 노드인가

| 필드 | 의미 |
| --- | --- |
| `hash` | 세션 안에서 커밋을 유일하게 식별하는 값 |
| `message` | 커밋 메시지. 키워드 역색인의 원본 데이터이기도 하다. |
| `author` | 커밋 작성자. 작성자 검색과 정렬의 기준이다. |
| `timestamp` | 커밋 생성 시각. 날짜 정렬의 기준이다. |
| `parents` | 부모 커밋들과의 연결을 표현하는 정보 |

명세는 커밋이 부모를 **0개 이상** 가질 수 있다고 한다. 첫 커밋은 기존 HEAD 커밋이 없으므로 부모가 없는 루트 커밋으로 이해할 수 있다. 이후 필수 `COMMIT` 명령은 현재 HEAD 커밋을 부모로 삼는다.

`parents`가 여러 부모를 표현할 수 있어야 한다는 자료구조 요구와, 필수 명령으로 실제 몇 개의 부모를 만드는지는 구분해야 한다.

### 브랜치와 HEAD는 어떻게 연결되는가

브랜치는 커밋을 가리키는 이름으로 이해할 수 있다. HEAD는 현재 작업 위치를 나타내며, 이 과제에서는 브랜치를 전환하면서 다음 커밋의 부모가 될 위치를 결정한다.

개념적으로는 다음 세 가지를 구분하면 된다. 실제 변수명이나 클래스 구성은 아직 정하지 않는다.

- 커밋 저장소: 생성된 커밋과 부모 관계를 보관한다.
- 브랜치 정보: 각 브랜치 이름이 어느 커밋을 가리키는지 보관한다.
- 현재 위치: 지금 선택한 브랜치와 그 브랜치가 가리키는 커밋을 알 수 있게 한다.

여기에 **현재 사용자 정보**를 구분해 두어야 한다(평가 2-1). `INIT`으로 설정한 현재 사용자는 이후 커밋을 생성할 때 작성자의 출처가 된다. 반면 각 커밋의 `author`는 그 커밋에 기록된 값이다. 현재 브랜치를 바꾼다고 기존 커밋의 작성자가 바뀌는 것은 아니다. 이렇게 책임을 구분하는 데 반드시 네 개의 클래스를 만들 필요는 없다.

예를 들어 `main`이 A를 가리킬 때 `BRANCH feature`를 실행하면 두 브랜치가 모두 A를 가리킨다. `SWITCH feature` 후 B를 커밋하면 B의 부모는 A이며, `feature`는 B로 이동한다. `main`은 A에 남는다. 이후 `main`으로 전환해 C를 커밋하면 C의 부모도 A다.

```text
부모 → 자식 방향으로 그린 관계

    A
   / \
  B   C
  ↑   ↑
feature main
```

브랜치를 생성한다고 기존 커밋을 복사하는 것은 아니다. 전환은 이미 존재하는 부모 관계를 바꾸는 동작도 아니다.

**스스로 설명해 보기:** 위 상황에서 B를 만든 뒤 `main`으로 전환하면, 다음 커밋의 부모가 B가 아닌 A인 이유는 무엇인가?

## 4. 그래프와 DAG

**근거: Subject.txt 3장 및 4장 「커밋 그래프」**

그래프는 노드와 노드 사이의 간선으로 관계를 표현하는 자료구조다. 이번 과제에서는 커밋이 노드이고, 커밋과 부모의 연결이 간선이다.

**DAG(Directed Acyclic Graph)**는 방향이 있고, 그 방향을 따라 이동해서 출발점으로 돌아오는 순환이 없는 그래프다. 커밋에서 부모를 따라갔을 때 자기 자신으로 돌아와서는 안 된다.

새 커밋이 이미 존재하는 커밋만 부모로 참조하고, 기존 부모 관계를 뒤집거나 수정하지 않는 생성 방식이라면 순환이 생기지 않는 이유를 설명할 수 있다. 별도의 그래프 검증 명령을 추가하라는 요구는 없다.

**사이클이 생기면 무엇이 문제인가? (평가 3-1)** A의 부모가 B이고 B의 부모가 A라면, 부모 우선 로그는 “B가 A보다 먼저”와 “A가 B보다 먼저”를 동시에 만족해야 하므로 불가능하다. 조상 관계에서도 자기 자신으로 돌아오게 된다. 방문 기록이 없으면 탐색이 끝나지 않거나 재귀가 계속될 수 있다. 방문 기록으로 반복 탐색을 막더라도, 순환 그래프가 올바른 커밋 이력이나 부모 우선 로그가 되는 것은 아니다.

### 저장 방향과 탐색 방향을 구분하기

`parents`를 따라가면 **자식 → 부모** 방향으로 이동한다. 그러나 모든 기능이 이 방향만 사용하는 것은 아니다.

| 기능 | 관계를 사용하는 방식 |
| --- | --- |
| 기본 `LOG` | 부모가 자식보다 먼저 나오도록 출력 순서를 구성한다. |
| `ANCESTORS` | 대상 커밋에서 부모 방향으로만 이동한다. |
| `PATH` | 커밋과 부모의 연결을 무방향으로 보고 양쪽으로 이동한다. |

DAG라는 말은 노드가 일렬로 이어져 있다는 뜻이 아니다. 분기와 여러 부모를 표현할 수 있고, 서로 연결되지 않은 부분이 있어도 DAG일 수 있다.

**스스로 설명해 보기:** 저장된 `parents` 간선을 그대로 따라간 순서와, 부모가 먼저 나오는 로그의 순서가 다른 이유는 무엇인가?

## 5. 커밋 식별자와 해시맵

**근거: Subject.txt 4장 「커밋 그래프」**

`hash`라는 필드 이름과 해시맵 자료구조는 구분해야 한다.

- **커밋 식별자 생성:** 서로 다른 커밋이 세션 안에서 같은 값을 갖지 않도록 하는 문제다. 명세는 증가 카운터나 난수 등 구현 방식을 허용하며, 특정 암호학적 해시 알고리즘을 요구하지 않는다.
- **커밋 조회:** 식별자를 받아 해당 커밋을 빠르게 찾는 문제다. `hash → commit` 형태의 해시맵으로 표현할 수 있다.

난수를 사용한다고 중복이 자동으로 불가능해지는 것은 아니다. 선택한 방식이 유일성을 어떻게 보장하는지 설명할 수 있어야 한다.

**두 종류의 충돌을 구분하기 (평가 2-2):** 서로 다른 커밋에 동일한 ID를 부여하는 문제는 애플리케이션이 막아야 한다. 같은 키로 커밋 저장소에 다시 넣으면 기존 커밋을 덮어쓸 수 있다. 반면 서로 다른 딕셔너리 키가 내부적으로 같은 해시값을 갖는 충돌은 딕셔너리가 키 비교 등을 통해 처리한다. Python의 `dict`를 사용한다면 이 내부 충돌 처리까지 직접 구현하라는 요구는 없다.

커밋이 V개일 때 리스트를 처음부터 확인하는 조회는 최악의 경우 O(V)다. 해시맵은 평균적으로 키 조회에 O(1)이 들지만, 충돌 등 불리한 조건에서는 O(V)가 될 수 있다. 따라서 “항상 O(1)”과 “평균 O(1)”을 구분해야 한다.

**스스로 설명해 보기:** 커밋 ID가 유일하더라도 리스트만 사용하면 조회가 느릴 수 있는 이유는 무엇인가?

## 6. 기본 LOG와 위상 정렬

**근거: Subject.txt 3장 및 4장 `LOG`**

기본 `LOG`는 **모든 부모가 해당 자식보다 먼저 출력되는 순서**를 요구한다. 단순히 최신순으로 나열하는 기능이 아니다.

위상 정렬은 선후 관계를 만족하도록 노드를 나열하는 방법이다. 부모를 먼저 처리해야 한다는 의존 관계를 기준으로 생각하면 된다. 저장된 간선이 자식 → 부모 방향이라면, 일반적인 위상 정렬 알고리즘의 간선 방향과 원하는 출력 방향을 맞춰야 한다.

위 예시의 A, B, C에서는 `A, B, C`와 `A, C, B`가 모두 부모 우선 조건을 만족한다. B와 C 사이에는 선후 관계가 없기 때문이다. 올바른 순서가 반드시 하나인 것은 아니다.

학습할 수 있는 대표 접근은 다음과 같다. 둘을 모두 구현해야 한다는 뜻은 아니다.

| 접근 | 핵심 생각 |
| --- | --- |
| Kahn 방식 | 아직 출력하지 않은 부모가 없는 커밋부터 처리하고, 연결된 자식의 남은 의존 관계를 갱신한다. |
| DFS의 후위 처리 | 부모들을 먼저 방문하고 처리한 뒤 현재 커밋을 결과에 넣는다. |

관련 연결 정보를 갖추고 노드와 간선을 한 번씩 처리하는 일반적인 위상 정렬은 O(V + E)다. V는 커밋 수, E는 부모 연결 수다. 매번 전체 커밋을 다시 훑어 자식을 찾는 구현이라면 같은 복잡도를 주장할 수 없다.

커밋 시각으로 정렬하는 것과 부모 우선 순서를 만드는 것은 서로 다른 기준이다. 평가 4-3은 작성자 정렬에 부모 우선 조건을 더하는 상황을 “강화된다면”이라는 가정으로 묻는다. 이는 기본 요구의 작성자 정렬과 부모 우선 로그를 별도 동작으로 해석하는 근거가 된다. 그 강화된 가정에 대한 학습은 14절에서 다룬다.

**스스로 설명해 보기:** 출력 결과가 `A, C, B`라고 해서 잘못된 로그라고 할 수 없는 이유는 무엇인가?

## 7. PATH와 너비 우선 탐색(BFS)

**근거: Subject.txt 4장 `PATH <commit1> <commit2>`**

이번 과제에서 경로의 길이는 **지나간 간선 수**다. 시각 차이, 메시지 길이 등은 경로 비용이 아니다. 또한 부모 연결을 무방향으로 취급하므로, 자식에서 부모로도 부모에서 자식으로도 이동할 수 있다.

위 예시에서 B에서 C로 가는 경로는 `B → A → C`이며, 길이는 2다. B의 부모 방향으로만 탐색하면 C에 도달하지 못한다.

**BFS(Breadth-First Search)**는 시작점에서 거리 0, 거리 1, 거리 2인 노드 순으로 탐색한다. 간선 비용이 동일한 그래프에서 최단 거리를 찾는 데 적합하다.

함께 알아야 할 개념은 다음과 같다.

- 큐: 먼저 들어온 항목을 먼저 꺼내며 탐색 순서를 유지한다.
- 방문 기록: 같은 노드를 반복 처리하거나 무방향 연결을 계속 왕복하지 않게 한다.
- 거리: 시작점에서 해당 노드까지 필요한 최소 간선 수를 기록한다.
- 경로 복원: 도착점까지의 거리뿐 아니라 실제 커밋 나열을 출력하기 위해, 어떤 경로로 도달했는지 추적한다.

인접 관계를 바로 조회하고 큐 연산을 효율적으로 처리한다면 일반 BFS 탐색은 O(V + E)다. 경로를 문자열로 만들거나 동률 후보를 비교하는 추가 비용은 별도로 살펴봐야 한다.

### 최단 거리만 맞으면 충분한가

명세는 같은 최단 길이의 경로가 여러 개이면 **`hash1->hash2->...`로 만든 전체 문자열의 사전순이 가장 작은 경로**를 선택하도록 요구한다.

따라서 “BFS에서 처음 발견한 경로”가 이 규칙을 만족하는지 따로 검토해야 한다. 딕셔너리나 집합의 순회 순서가 곧 명세의 동률 처리 기준인 것은 아니다. 해시를 숫자로 비교하는 것과 경로 문자열을 사전순으로 비교하는 것도 구분해야 한다.

경로가 없을 때의 결과인 `No path`와, 입력 해시가 존재하지 않을 때의 `Unknown commit: <hash>`는 서로 다른 상황이다.

**스스로 설명해 보기:** BFS가 최단 간선 수를 보장하는 이유와, 그것만으로 사전순 규칙까지 자동으로 보장되지는 않는 이유는 무엇인가?

## 8. ANCESTORS와 도달 가능성

**근거: Subject.txt 4장 `ANCESTORS <commit_hash>`**

조상은 대상 커밋의 부모, 부모의 부모처럼 **부모 방향을 따라 도달할 수 있는 커밋**이다. 대상 커밋 자신은 조상이 아니다. 부모가 없는 커밋의 조상 목록은 비어 있다.

모든 조상을 찾는 데는 DFS나 BFS를 사용할 수 있다. DFS(Depth-First Search)는 한 방향을 깊게 따라간 뒤 다른 연결을 살피며, 스택이나 재귀 호출로 탐색 상태를 관리할 수 있다. 이 기능의 핵심은 최단 거리보다 빠짐없는 도달 노드 수집이다.

여러 부모 경로가 같은 조상에 도달할 수 있으므로 방문 기록의 역할을 이해해야 한다. DAG에 순환이 없더라도 같은 노드에 이르는 경로가 하나뿐이라는 보장은 없다.

도달 가능한 조상과 시작점을 포함한 노드 수를 Vᵣ, 그 탐색에서 확인하는 부모 간선 수를 Eᵣ라고 하면, 방문 기록을 사용하는 일반적인 탐색은 O(Vᵣ + Eᵣ)다. 명세는 조상 출력 순서를 따로 지정하지 않는다.

**스스로 설명해 보기:** `PATH`용 무방향 탐색을 조상 조회에 그대로 사용하면 왜 형제나 자식까지 결과에 섞일 수 있는가?

## 9. 직접 구현하는 정렬

**근거: Subject.txt 3장, 4장 「정렬 알고리즘 직접 구현」 및 `LOG --sort-by=date|author`, 7장**

정렬은 비교 기준에 따라 원소를 재배치하는 과정이다. 이 과제에서는 같은 커밋 목록에 대해 `timestamp` 기준과 `author` 기준을 적용할 수 있어야 한다.

**정렬 절차**와 **비교 기준**을 나누어 생각하면, 알고리즘 전체를 날짜용·작성자용으로 각각 복제하지 않고 기준을 바꾸는 구조를 설계할 수 있다. 구체적인 함수 형태는 구현 단계에서 다룬다.

### 평균·최악 시간복잡도

평균 시간복잡도는 입력에 관한 가정 아래 일반적으로 드는 비용이고, 최악 시간복잡도는 가장 불리한 입력에서 드는 비용이다. 실제 측정 시간과는 구분된다.

다음은 선택 가능한 정렬 알고리즘의 학습 예시다. 실제 사용할 알고리즘은 구현 단계에서 정한다.

| 알고리즘 | 핵심 생각 | 평균 | 최악 | 안정성 |
| --- | --- | --- | --- | --- |
| 삽입 정렬 | 앞쪽의 정렬된 구간에서 현재 원소가 들어갈 위치를 찾는다. | O(n²) | O(n²) | 같은 키의 원소를 서로 추월시키지 않으면 안정적이다. |
| 병합 정렬 | 목록을 나누어 각각 정렬하고 두 정렬 결과를 합친다. | O(n log n) | O(n log n) | 병합 시 키가 같으면 왼쪽 원소를 먼저 선택하는 방식으로 안정성을 유지할 수 있다. |

표는 일반적인 비교 기반 구현을 기준으로 하며, 삽입 정렬의 평균은 입력 순서가 무작위라고 보는 경우다. 병합 정렬은 나누는 단계 수와 각 단계의 병합 비용을 연결해서 복잡도를 설명할 수 있어야 한다.

### 안정 정렬

안정 정렬은 **비교 키가 같은 원소끼리 입력에서의 상대 순서를 유지하는 정렬**이다. 서로 다른 키의 순서를 그대로 둔다는 뜻이 아니다.

입력에서 작성자가 같은 A와 B가 이 순서로 있었다면, 작성자 기준의 안정 정렬 후에도 A가 B보다 앞선다. 명세는 동률 처리 규칙을 자유롭게 정하도록 하므로 안정 정렬 자체가 필수 조건은 아니다. 다만 자신이 구현한 정렬이 안정적인지 설명할 수 있어야 한다.

표준 정렬 API 금지는 로그 정렬뿐 아니라 다른 기능에서 정렬이 필요할 때도 적용된다. 예를 들어 경로 동률 처리에 정렬을 사용하더라도 `sorted()`에 맡길 수 없다.

**스스로 설명해 보기:** 선택한 알고리즘의 평균·최악 복잡도는 무엇이며, 코드에서 어떤 비교 조건이 안정성에 영향을 주는가?

## 10. 역색인과 검색

**근거: Subject.txt 3장 및 4장 「역색인」·`COMMIT`·`SEARCH`**

일반적인 커밋 저장소는 커밋 ID로 메시지를 찾는다. **역색인(Inverted Index)**은 반대로 키워드나 작성자로 관련 커밋 ID들을 찾게 한다.

명세가 요구하는 두 연결은 다음과 같다.

```text
keyword → commit_hash 목록
author  → commit_hash 목록
```

예를 들어 A의 메시지가 `Add login feature`, B의 메시지가 `Fix login`이고 두 작성자가 Alice라면, 키워드 `login`은 A와 B에 연결되고 작성자 `Alice`도 A와 B에 연결된다.

### 토큰화와 정규화

- 토큰화: 메시지를 공백 기준으로 분리한다. 위 A 메시지에서는 `Add`, `login`, `feature`가 나온다.
- 정규화: 각 토큰을 소문자로 바꾼다. `Add`는 `add`로 저장된다.
- 색인 갱신: 새 커밋을 만들 때 작성자와 메시지 토큰에 해당 커밋 ID를 연결한다.

명세의 최소 추출 규칙은 `split`과 `lower`다. 구두점 제거, 어간 추출, 유사어 검색 등은 요구되지 않는다. 예를 들어 이 규칙만 적용하면 `login`과 `login,`은 다른 토큰이다.

검색 키워드에도 저장 시와 일치하는 정규화가 필요하다는 점을 생각해야 한다. 다만 메시지 토큰에 대한 소문자 규칙을 작성자나 브랜치 이름에까지 자동으로 확대하면 안 된다. 명령어의 대소문자 무시 규칙도 인자 전체를 소문자로 바꾸라는 뜻은 아니다.

같은 메시지에 `login`이 반복되어도 “일치하는 커밋 목록”과 “단어가 나온 횟수”는 다른 결과다. 색인에 연결을 저장하는 방식이 검색 결과에 중복 커밋을 만들지 않는지 생각해 볼 필요가 있다.

### 전체 순회보다 왜 빠른가

전체 순회 검색은 매번 모든 커밋의 메시지나 작성자를 확인한다. 커밋이 V개이면 적어도 V개 항목을 살피고, 메시지 검사 비용까지 든다.

해시맵 기반 역색인의 단일 키 조회는 평균 O(1)에 후보 목록을 찾을 수 있다. 결과가 k개이면 커밋 조회와 출력에 O(k)가 더 들므로, **조회와 결과 나열을 합쳐 평균 O(1 + k)**로 설명할 수 있다. 여기서는 키와 개별 결과의 문자열 길이에 따른 비용을 별도로 둔다.

이 속도는 준비 비용을 없앤 결과가 아니다. 커밋 생성 시 메시지 토큰을 추출하고 인덱스를 갱신하는 시간과, 키워드·작성자별 연결을 보관하는 추가 메모리가 필요하다. 검색마다 모든 커밋을 읽어서 역색인을 새로 만들면 명세가 요구한 이점을 얻을 수 없다.

### 갱신 시점과 데이터의 일치 (평가 2-3)

명세의 갱신 시점은 **커밋 생성 시**다. 성공한 `COMMIT` 다음에 곧바로 `SEARCH`를 실행해도 새 커밋을 찾을 수 있어야 한다. 자신의 설계를 설명할 때는 다음 정보의 연결을 짚어 본다.

- 새 커밋의 고유 ID와 작성자·메시지를 확정하고 커밋 저장소에 등록하는 부분
- 작성자를 키로 삼아 그 커밋 ID를 연결하는 부분
- 메시지에서 소문자 토큰을 추출해 각 키워드에 같은 커밋 ID를 연결하는 부분

커밋만 저장하고 색인을 빠뜨리면 검색 결과에서 누락된다. 반대로 존재하지 않는 커밋 ID가 색인에 들어가면 결과를 조회할 수 없다. 평가에서는 이런 연결이 한 번의 커밋 생성 과정에서 어디서 이루어지는지 자신의 코드로 설명하면 된다. 트랜잭션 시스템 같은 별도의 기능을 추가하라는 뜻은 아니다.

**스스로 설명해 보기:** 결과가 모든 커밋에 해당한다면 역색인이 있어도 출력 비용이 O(V)가 될 수 있는 이유는 무엇인가?

## 11. REPL, 명령 파싱, 책임 분리

**근거: Subject.txt 2장 「CLI 인터페이스」, 4장 「CLI 공통 규칙」, 7장 「구조/품질」**

**REPL(Read–Eval–Print Loop)**은 입력을 읽고, 해석·실행하고, 결과를 출력하는 과정을 반복하는 구조다. 이 과제에서는 `mini-git>` 프롬프트에서 명령을 받으며 `exit` 또는 `quit`로 종료한다.

파싱은 입력 문자열을 명령어, 인자, 옵션으로 구분하는 과정이다. 다음 입력에서는 메시지 전체가 하나의 인자여야 한다.

```text
COMMIT "Add login feature"
```

입력 전체에 단순 공백 분리만 적용하면 따옴표 안의 공백까지 나뉜다. **명령행을 파싱하는 규칙**과 **커밋 메시지에서 검색 토큰을 추출하는 규칙**은 서로 다르다는 점을 이해해야 한다.

옵션 형태는 `SEARCH --author=<name>`과 `LOG --sort-by=date|author`다. 여기서 `date|author`는 허용 값 두 개를 뜻하며, 실제로는 `--sort-by=date` 또는 `--sort-by=author`를 입력한다.

입력 개수나 옵션 형식이 잘못된 상황과, 형식은 맞지만 대상 브랜치·커밋이 없는 상황을 구분한다. 명세는 최소 에러 메시지의 예로 `Invalid args`, `Unknown branch: <name>`, `Unknown commit: <hash>`를 제시한다.

탐색·정렬·인덱싱을 독립된 함수 또는 클래스로 나누면, 입력을 읽는 과정과 알고리즘이 결과를 만드는 과정을 구분해서 설명할 수 있다. 엔트리 포인트 1개라는 제출 조건이 모든 로직을 한 함수에 넣으라는 뜻은 아니다. 특정 클래스 수나 파일 수는 명세에서 정하지 않는다.

### 그래프 로직을 재사용한다는 뜻 (평가 2-4)

그래프 접근과 알고리즘의 입출력을 CLI로부터 분리하면 같은 함수를 REPL 외부에서도 호출해 결과를 확인할 수 있다. 커밋 조회나 부모 관계 조회처럼 의미가 같은 부분은 공유할 수 있다.

다만 `LOG`는 부모 우선 순서, `PATH`는 무방향 최단 경로, `ANCESTORS`는 부모 방향의 도달 가능성을 다룬다. 재사용을 위해 세 기능을 무조건 같은 BFS 함수에 넣으면 목적이 다른 부분까지 섞일 수 있다. 무엇을 공유하고 무엇을 각 알고리즘의 책임으로 남겼는지 설명하는 것이 핵심이다. 이를 위해 별도의 범용 그래프 프레임워크를 만들 필요는 없다.

### 주석과 docstring의 작성 기준 (평가 2-5)

주요 함수·클래스에는 그 역할과 사용 규칙을 설명한다. 구체적으로 입력·반환값, 변경하는 상태가 있는지, 알고리즘이 사용하는 방향이나 비교 기준을 살필 수 있다.

예를 들어 경로 탐색에는 “무방향 연결에서 간선 수가 최소인 경로를 찾는다”는 설명이 중요하다. 커밋 생성에는 커밋 저장소·현재 브랜치·역색인 중 무엇이 갱신되는지 드러나야 한다. 주석은 코드 한 줄을 그대로 한국어로 반복하기보다, 방문 기록이나 동률 처리처럼 이유를 알아야 하는 선택을 설명하는 데 쓸 수 있다.

이 항목들은 문서를 작성하는 판단 기준이며, 명세가 정하지 않은 고정된 docstring 형식을 요구하는 것은 아니다.

**스스로 설명해 보기:** `COMMIT`이라는 명령어의 대소문자를 무시하면서 메시지 원문은 보존하려면, 입력의 어느 부분에 어떤 처리를 해야 하는가?

## 12. 명세에서 확정하지 않은 부분

다음은 구현 결정을 내리기 전에 명세의 범위를 구분하기 위한 메모다. 추가 기능 요구나 확정된 동작으로 취급하지 않는다. 명백한 모순으로 판단되는 경우에는 사용자와 의논한 뒤 방향을 정한다.

| 항목 | 명세에서 확인되는 내용 | 아직 확정하지 않은 해석 |
| --- | --- | --- |
| 공백이 포함된 검색어 | 검색 키워드에 공백을 허용하며, 색인은 공백으로 나눈 소문자 토큰을 저장한다. | `SEARCH "login feature"`가 구문 일치인지, 여러 토큰의 AND/OR 검색인지 지정하지 않는다. 인자를 하나로 읽는 문제와 검색 의미를 결정하는 문제를 구분해야 한다. |
| 키워드의 “포함” 의미 | 토큰 기반 역색인과 “키워드가 포함된 커밋 메시지”를 요구한다. | `log`가 `login`에도 일치해야 하는지는 명확하지 않다. 부분 문자열 검색을 임의로 필수화하지 않는다. |
| 기본 LOG와 정렬 옵션 | 기본 `LOG`에는 부모 우선 규칙이 있고, 옵션에는 날짜·작성자 정렬 규칙이 있다. 평가 4-3은 작성자 정렬에 부모 우선 조건을 더하는 상황을 가정한다. | 평가지 문구는 기존 작성자 정렬에는 부모 우선 조건을 추가하지 않는 해석을 뒷받침한다. 강화된 조건은 응용 질문으로 다룬다. |
| LOG가 조회할 커밋의 범위 | 결과 예시에는 현재 브랜치와 다른 브랜치의 커밋이 함께 나온다. | 기능 본문은 조회 범위를 별도로 정의하지 않는다. 예시는 저장소 전체 로그를 시사하지만, 실제 Git의 기본 로그 범위를 그대로 가져오면 안 된다. |
| 날짜·작성자 정렬 방향 | 각각 timestamp와 작성자 이름을 기준으로 하며 동률 처리는 자유다. | 오름차순·내림차순은 명시하지 않는다. 구현할 때 선택할 사항이다. |
| 초기화 및 빈 상태 | `INIT`은 저장소·main·HEAD·현재 사용자를 설정한다. 커밋은 부모 0개 이상을 허용한다. | 반복 `INIT`의 처리나 커밋이 없는 상태에서의 일부 명령 동작은 세부적으로 지정하지 않는다. 별도의 사용자 변경 명령도 요구하지 않는다. |

기능을 구현할 때는 **명시된 요구사항**, **학습을 위한 구현 선택**, **해석이 필요한 부분**을 구분해서 검토한다.

## 13. 평가 질문을 자신의 구현과 연결하기

**근거: evaluate.txt 항목 1~3, Subject.txt 3장·4장·7장**

항목 1은 실제 기능의 동작 확인이다. 초기화와 브랜치 이동은 3절, 부모 우선 로그는 6절, 경로와 조상 탐색은 7~8절, 검색과 정렬은 9~10절에 연결된다. 평가 문항은 기능을 요약하므로, 문항에 반복해서 적히지 않은 `PATH`의 사전순 동률 처리나 CLI 따옴표 규칙도 `Subject.txt`에 따라 지켜야 한다.

항목 2~3은 개념을 아는 것과 실제 코드의 선택을 연결해 설명하는 평가다. 아직 구현하지 않은 부분을 “구현했다”고 답하는 대신, 구현을 마친 뒤 아래 연결을 자신의 함수·자료형으로 설명해 본다.

| 3-2 부모 우선 LOG | 6절: 의존 관계와 출력 시점 | 부모가 출력되기 전에 자식이 출력되지 않는 이유는 무엇인가? |
| 3-3 최단 경로와 간선 정의 | 7절: BFS와 무방향 연결 | 최단 간선 수를 보장하는 이유는 무엇이며, 부모·자식 양쪽으로 어떻게 이동하는가? |

`PATH`를 무방향으로 정의한 직접적인 근거는 `Subject.txt`의 명시적인 요구다. 그 효과는 공통 조상을 거쳐 서로 다른 가지의 커밋 사이에도 경로를 찾을 수 있다는 것이다. BFS 자체가 무방향 그래프에서만 동작하기 때문이라고 설명하면 안 된다. BFS는 방향 그래프에서도 허용된 간선을 따라 최단 거리를 구할 수 있다.

## 14. 조건 변경을 가정한 응용 질문

**근거: evaluate.txt 항목 4**

아래는 평가에서 제시한 가정에 대한 학습이다. 현재 `PATH`를 방향 그래프로 바꾸거나, 정렬 기능·해시 생성 방식을 더 추가하는 구현 지시가 아니다.

### 평가 4-1. 커밋 수가 10배 늘면 어디가 병목이 되는가

먼저 입력 크기의 의미를 정해야 한다. V는 커밋 수, E는 부모 연결 수, k는 검색 결과 수다. 커밋당 부모 수와 메시지 길이가 비슷하게 유지된다면 V가 10배일 때 E와 전체 메시지 분량도 대략 10배가 된다. 그래프 연결 밀도나 메시지 길이까지 크게 변하면 예측은 달라진다.

| 처리 방식 | 크기가 10배일 때 예상되는 연산량 변화 | 설명할 수 있는 개선 방향 |
| --- | --- | --- |
| 해시맵으로 커밋 1개 조회 | 평균 O(1)이므로 V 때문에 조회 횟수가 10배로 늘지는 않는다. 저장 메모리는 증가한다. | 조회 시 해시맵을 사용하는지 확인한다. |
| 전체 커밋을 훑는 검색 | 메시지 길이가 비슷하면 대략 10배 | 이미 요구된 역색인으로 후보를 직접 조회한다. 결과 k개를 출력하는 비용은 남는다. |
| 인접 관계를 이용한 BFS·DFS·위상 정렬 | O(V + E)이므로 위 가정에서 대략 10배 | 각 노드·간선의 반복 처리를 피하고, 필요한 인접 관계를 바로 조회한다. |
| 방문 노드마다 전체 커밋을 훑어 자식 찾기 | V개 노드 각각에서 V개를 확인하면 O(V²), 대략 100배 | 탐색에 필요한 양방향 인접 관계 등을 준비하는 비용과 반복 순회의 비용을 비교한다. |
| O(V²) 정렬 | 대략 100배 | 입력 규모에 따라 O(V log V) 정렬을 선택하는 이유를 설명한다. |
| O(V log V) 정렬 | 약 `10 × log(10V) / log(V)`배 | 단순히 항상 10배라고 하지 않고 로그 항의 증가도 고려한다. |
| 로그·검색 결과 출력 | 결과 수가 10배이면 비슷한 길이의 출력도 대략 10배 | 모든 결과를 출력해야 한다면 그 비용 자체를 없앨 수는 없다. |

자료구조의 작은 연산도 살펴야 한다. 예를 들어 Python 리스트의 맨 앞 원소를 삭제하면 뒤 원소들을 이동시켜야 하므로, BFS에서 반복하면 큐 처리 비용이 커질 수 있다. 큐를 어떤 방식으로 관리해야 불필요한 이동을 피할 수 있는지 설명해 본다.

개선 방향은 자신이 선택한 구현에서 실제로 발생하는 반복 작업을 근거로 말한다. 이 질문은 벤치마크 명령이나 캐시 같은 새 기능을 필수로 요구하지 않는다. `PATH`의 사전순 후보 비교 비용도 일반 BFS 비용과 별도로 고려해야 한다.

### 평가 4-2. PATH에서 부모 방향만 허용하면 무엇이 달라지는가

3절의 예시에서 B와 C는 모두 A의 자식이다. 현재 요구사항에서는 연결을 무방향으로 보므로 B에서 C까지 `B → A → C`로 이동할 수 있다.

부모 방향만 허용한다는 가정에서는 B → A는 가능하지만 A → C는 불가능하다. 따라서 B에서 C로는 경로가 없고, B에서 A로는 길이 1의 경로가 있다. A에서 B로는 갈 수 없으므로 경로 존재 여부도 더 이상 대칭적이지 않다.

구현에서 바뀌는 핵심은 **현재 노드에서 다음으로 이동할 수 있는 이웃의 정의**다. 부모와 자식을 모두 후보로 삼던 부분에서 부모만 후보로 삼게 된다. 모든 간선의 비용이 여전히 1이므로 BFS를 최단 경로 탐색에 계속 사용할 수 있다. 최단 경로 동률 규칙 등 바뀌지 않은 요구는 그대로 고려한다.

### 평가 4-3. 작성자 정렬에 부모 우선 조건도 더한다면

먼저 두 조건이 항상 함께 성립할 수 있는지 살핀다. 부모 P의 작성자가 Zoe이고 자식 C의 작성자가 Alice라고 하자. 작성자 오름차순만 보면 C가 먼저지만, 부모 우선 조건에서는 P가 먼저다. **전체 목록의 작성자 오름차순과 부모 우선 순서를 언제나 동시에 만족시킬 수는 없다.**

따라서 강화된 요구가 실제로 주어진다면 어떤 조건을 우선하는지 정의해야 한다. 해결 전략의 한 예는 **부모 우선 조건을 지키면서, 지금 출력 가능한 커밋들 중 작성자 순으로 선택하는 것**이다. 오름차순은 이 설명을 위한 예시이며 원래 명세에 정해진 방향은 아니다.

이 전략은 Kahn 방식과 연결된다.

1. 아직 출력되지 않은 부모가 없는 커밋들을 선택 가능한 후보로 둔다.
2. 그 후보들 사이에서 작성자 기준으로 다음 커밋을 고른다.
3. 선택한 커밋을 출력하고 자식들의 남은 부모 수를 갱신한다.
4. 모든 부모가 출력된 자식은 다음 선택 후보가 된다.

결과는 부모 관계를 만족하는 로그이며, 작성자 기준은 선택 가능한 후보 사이의 우선순위다. 위상 정렬 결과를 나중에 작성자로 전체 재정렬하면 부모 우선 조건이 다시 깨질 수 있다. 작성자가 같은 항목의 순서를 보존하는 안정 정렬만으로도 이 문제는 해결되지 않는다.

이 설명이 특정 후보 관리 자료구조나 추가 정렬 기능의 구현을 요구하는 것은 아니다. 구현한다면 표준 정렬 API 금지는 여전히 적용되며, 후보 선택에 드는 비용도 전체 복잡도에 포함해야 한다.

### 평가 4-4. 카운터와 난수 방식은 테스트·재현성·디버깅에 어떤 차이가 있는가

두 방식 모두 명세가 허용한다. 중요한 조건은 세션 안에서 커밋 ID가 중복되지 않는 것이다.

| 관점 | 카운터 기반 | 난수 기반 |
| --- | --- | --- |
| 유일성 | 같은 세션에서 사용한 번호를 재사용하지 않도록 관리하면 설명하기 쉽다. | 중복 가능성이 낮다는 것과 없다는 것은 다르다. 기존 ID 확인과 중복 시 대응이 필요하다. |
| 재현성 | 같은 시작 상태와 같은 생성 순서라면 같은 ID를 얻기 쉽다. | 같은 명령을 실행해도 ID가 달라질 수 있다. 의사난수의 생성 조건과 호출 순서를 통제하면 재현에 도움이 된다. |
| 테스트 | 예상 ID와 부모 연결을 고정된 예시로 확인하기 쉽다. | 생성된 ID를 받아 관계를 확인하거나, 테스트에서 제어 가능한 난수 공급으로 중복 상황을 만들 수 있다. |
| 디버깅 | ID로 생성 순서를 파악하기 쉬워 이력 추적에 도움이 된다. | ID만으로 생성 순서를 추정하기 어렵다. timestamp·message·parents를 함께 살펴야 한다. |

난수 생성에서 같은 seed를 사용하는 것은 의사난수 수열의 재현을 위한 수단이지 ID 중복을 막는 수단이 아니다. 중복이 실제로 나오도록 입력을 통제했을 때 기존 커밋을 덮어쓰지 않는지 설명하는 것과, 여러 번 실행해서 우연히 중복이 없었음을 확인하는 것은 다르다. 이 역시 테스트 관점을 묻는 학습이며, seed 설정 CLI 옵션을 추가하라는 요구는 아니다.

해시 문자열이 달라지면 `PATH`의 사전순 동률 결과도 달라질 수 있다. 따라서 서로 다른 ID 생성 방식의 실행 결과를 비교할 때는 최단 길이와 부모 관계뿐 아니라, 그 실행에서 생성된 실제 해시 문자열을 기준으로 동률 규칙을 확인해야 한다.
