## 2. 학습 범위와 제약

**근거: Subject.txt 2장, 6장, 7장**

- Python 3.10 이상에서 동작하는 CLI 프로그램을 만든다. 엔트리 포인트와 `README.md`가 필수 제출물이다.
- 다루는 데이터는 커밋의 메타데이터다. 파일 내용 추적과 네트워크 통신은 구현 범위에서 제외된다.
- 메모리에서 동작하면 충분하다. 데이터를 파일에 저장하고 다음 실행에서 복구하는 기능은 필수가 아니다.
- 그래프 전용 라이브러리와 정렬 관련 표준 API를 사용할 수 없다. `sorted()`와 `list.sort()`도 금지된다.
- 탐색·정렬·인덱싱 로직은 독립된 함수 또는 클래스로 분리하고, 주요 함수·클래스에는 주석 또는 docstring을 작성한다.

소개에 등장하는 rebase와 cherry-pick은 구현 요구사항이 아니다. 실제 Git의 모든 동작을 재현하는 것이 이 과제의 완료 기준은 아니다.

## 3. 커밋, 브랜치, HEAD

**근거: Subject.txt 4장 「커밋 그래프」 및 `INIT`·`BRANCH`·`SWITCH`·`COMMIT`**

### 커밋은 어떤 정보를 가진 노드인가

| 필드 | 의미 |
| --- | --- |
| `hash` | 세션 안에서 커밋을 유일하게 식별하는 값 |
| `message` | 커밋 메시지. 키워드 역색인의 원본 데이터이기도 하다. |
| `author` | 커밋 작성자. 작성자 검색과 정렬의 기준이다. |
| `timestamp` | 커밋 생성 시각. 날짜 정렬의 기준이다. |
| `parents` | 부모 커밋들과의 연결을 표현하는 정보 |

명세는 커밋이 부모를 **0개 이상** 가질 수 있다고 한다. 첫 커밋은 기존 HEAD 커밋이 없으므로 부모가 없는 루트 커밋으로 이해할 수 있다. 이후 필수 `COMMIT` 명령은 현재 HEAD 커밋을 부모로 삼는다.

`parents`가 여러 부모를 표현할 수 있어야 한다는 자료구조 요구와, 필수 명령으로 실제 몇 개의 부모를 만드는지는 구분해야 한다.

### 브랜치와 HEAD는 어떻게 연결되는가

브랜치는 커밋을 가리키는 이름으로 이해할 수 있다. HEAD는 현재 작업 위치를 나타내며, 이 과제에서는 브랜치를 전환하면서 다음 커밋의 부모가 될 위치를 결정한다.

개념적으로는 다음 세 가지를 구분하면 된다. 실제 변수명이나 클래스 구성은 아직 정하지 않는다.

- 커밋 저장소: 생성된 커밋과 부모 관계를 보관한다.
- 브랜치 정보: 각 브랜치 이름이 어느 커밋을 가리키는지 보관한다.
- 현재 위치: 지금 선택한 브랜치와 그 브랜치가 가리키는 커밋을 알 수 있게 한다.

여기에 **현재 사용자 정보**를 구분해 두어야 한다(평가 2-1). `INIT`으로 설정한 현재 사용자는 이후 커밋을 생성할 때 작성자의 출처가 된다. 반면 각 커밋의 `author`는 그 커밋에 기록된 값이다. 현재 브랜치를 바꾼다고 기존 커밋의 작성자가 바뀌는 것은 아니다. 이렇게 책임을 구분하는 데 반드시 네 개의 클래스를 만들 필요는 없다.

예를 들어 `main`이 A를 가리킬 때 `BRANCH feature`를 실행하면 두 브랜치가 모두 A를 가리킨다. `SWITCH feature` 후 B를 커밋하면 B의 부모는 A이며, `feature`는 B로 이동한다. `main`은 A에 남는다. 이후 `main`으로 전환해 C를 커밋하면 C의 부모도 A다.

```text
부모 → 자식 방향으로 그린 관계

    A
   / \
  B   C
  ↑   ↑
feature main
```

브랜치를 생성한다고 기존 커밋을 복사하는 것은 아니다. 전환은 이미 존재하는 부모 관계를 바꾸는 동작도 아니다.

**스스로 설명해 보기:** 위 상황에서 B를 만든 뒤 `main`으로 전환하면, 다음 커밋의 부모가 B가 아닌 A인 이유는 무엇인가?

## 4. 그래프와 DAG

**근거: Subject.txt 3장 및 4장 「커밋 그래프」**

그래프는 노드와 노드 사이의 간선으로 관계를 표현하는 자료구조다. 이번 과제에서는 커밋이 노드이고, 커밋과 부모의 연결이 간선이다.

**DAG(Directed Acyclic Graph)**는 방향이 있고, 그 방향을 따라 이동해서 출발점으로 돌아오는 순환이 없는 그래프다. 커밋에서 부모를 따라갔을 때 자기 자신으로 돌아와서는 안 된다.

새 커밋이 이미 존재하는 커밋만 부모로 참조하고, 기존 부모 관계를 뒤집거나 수정하지 않는 생성 방식이라면 순환이 생기지 않는 이유를 설명할 수 있다. 별도의 그래프 검증 명령을 추가하라는 요구는 없다.

**사이클이 생기면 무엇이 문제인가? (평가 3-1)** A의 부모가 B이고 B의 부모가 A라면, 부모 우선 로그는 “B가 A보다 먼저”와 “A가 B보다 먼저”를 동시에 만족해야 하므로 불가능하다. 조상 관계에서도 자기 자신으로 돌아오게 된다. 방문 기록이 없으면 탐색이 끝나지 않거나 재귀가 계속될 수 있다. 방문 기록으로 반복 탐색을 막더라도, 순환 그래프가 올바른 커밋 이력이나 부모 우선 로그가 되는 것은 아니다.

### 저장 방향과 탐색 방향을 구분하기

`parents`를 따라가면 **자식 → 부모** 방향으로 이동한다. 그러나 모든 기능이 이 방향만 사용하는 것은 아니다.

| 기능 | 관계를 사용하는 방식 |
| --- | --- |
| 기본 `LOG` | 부모가 자식보다 먼저 나오도록 출력 순서를 구성한다. |
| `ANCESTORS` | 대상 커밋에서 부모 방향으로만 이동한다. |
| `PATH` | 커밋과 부모의 연결을 무방향으로 보고 양쪽으로 이동한다. |

DAG라는 말은 노드가 일렬로 이어져 있다는 뜻이 아니다. 분기와 여러 부모를 표현할 수 있고, 서로 연결되지 않은 부분이 있어도 DAG일 수 있다.

**스스로 설명해 보기:** 저장된 `parents` 간선을 그대로 따라간 순서와, 부모가 먼저 나오는 로그의 순서가 다른 이유는 무엇인가?

## 5. 커밋 식별자와 해시맵

**근거: Subject.txt 4장 「커밋 그래프」**

`hash`라는 필드 이름과 해시맵 자료구조는 구분해야 한다.

- **커밋 식별자 생성:** 서로 다른 커밋이 세션 안에서 같은 값을 갖지 않도록 하는 문제다. 명세는 증가 카운터나 난수 등 구현 방식을 허용하며, 특정 암호학적 해시 알고리즘을 요구하지 않는다.
- **커밋 조회:** 식별자를 받아 해당 커밋을 빠르게 찾는 문제다. `hash → commit` 형태의 해시맵으로 표현할 수 있다.

난수를 사용한다고 중복이 자동으로 불가능해지는 것은 아니다. 선택한 방식이 유일성을 어떻게 보장하는지 설명할 수 있어야 한다.

**두 종류의 충돌을 구분하기 (평가 2-2):** 서로 다른 커밋에 동일한 ID를 부여하는 문제는 애플리케이션이 막아야 한다. 같은 키로 커밋 저장소에 다시 넣으면 기존 커밋을 덮어쓸 수 있다. 반면 서로 다른 딕셔너리 키가 내부적으로 같은 해시값을 갖는 충돌은 딕셔너리가 키 비교 등을 통해 처리한다. Python의 `dict`를 사용한다면 이 내부 충돌 처리까지 직접 구현하라는 요구는 없다.

커밋이 V개일 때 리스트를 처음부터 확인하는 조회는 최악의 경우 O(V)다. 해시맵은 평균적으로 키 조회에 O(1)이 들지만, 충돌 등 불리한 조건에서는 O(V)가 될 수 있다. 따라서 “항상 O(1)”과 “평균 O(1)”을 구분해야 한다.

**스스로 설명해 보기:** 커밋 ID가 유일하더라도 리스트만 사용하면 조회가 느릴 수 있는 이유는 무엇인가?

## 6. 기본 LOG와 위상 정렬

**근거: Subject.txt 3장 및 4장 `LOG`**

기본 `LOG`는 **모든 부모가 해당 자식보다 먼저 출력되는 순서**를 요구한다. 단순히 최신순으로 나열하는 기능이 아니다.

위상 정렬은 선후 관계를 만족하도록 노드를 나열하는 방법이다. 부모를 먼저 처리해야 한다는 의존 관계를 기준으로 생각하면 된다. 저장된 간선이 자식 → 부모 방향이라면, 일반적인 위상 정렬 알고리즘의 간선 방향과 원하는 출력 방향을 맞춰야 한다.

위 예시의 A, B, C에서는 `A, B, C`와 `A, C, B`가 모두 부모 우선 조건을 만족한다. B와 C 사이에는 선후 관계가 없기 때문이다. 올바른 순서가 반드시 하나인 것은 아니다.

학습할 수 있는 대표 접근은 다음과 같다. 둘을 모두 구현해야 한다는 뜻은 아니다.

| 접근 | 핵심 생각 |
| --- | --- |
| Kahn 방식 | 아직 출력하지 않은 부모가 없는 커밋부터 처리하고, 연결된 자식의 남은 의존 관계를 갱신한다. |
| DFS의 후위 처리 | 부모들을 먼저 방문하고 처리한 뒤 현재 커밋을 결과에 넣는다. |

관련 연결 정보를 갖추고 노드와 간선을 한 번씩 처리하는 일반적인 위상 정렬은 O(V + E)다. V는 커밋 수, E는 부모 연결 수다. 매번 전체 커밋을 다시 훑어 자식을 찾는 구현이라면 같은 복잡도를 주장할 수 없다.

커밋 시각으로 정렬하는 것과 부모 우선 순서를 만드는 것은 서로 다른 기준이다. 평가 4-3은 작성자 정렬에 부모 우선 조건을 더하는 상황을 “강화된다면”이라는 가정으로 묻는다. 이는 기본 요구의 작성자 정렬과 부모 우선 로그를 별도 동작으로 해석하는 근거가 된다. 그 강화된 가정에 대한 학습은 14절에서 다룬다.

**스스로 설명해 보기:** 출력 결과가 `A, C, B`라고 해서 잘못된 로그라고 할 수 없는 이유는 무엇인가?

## 7. PATH와 너비 우선 탐색(BFS)

**근거: Subject.txt 4장 `PATH <commit1> <commit2>`**

이번 과제에서 경로의 길이는 **지나간 간선 수**다. 시각 차이, 메시지 길이 등은 경로 비용이 아니다. 또한 부모 연결을 무방향으로 취급하므로, 자식에서 부모로도 부모에서 자식으로도 이동할 수 있다.

위 예시에서 B에서 C로 가는 경로는 `B → A → C`이며, 길이는 2다. B의 부모 방향으로만 탐색하면 C에 도달하지 못한다.

**BFS(Breadth-First Search)**는 시작점에서 거리 0, 거리 1, 거리 2인 노드 순으로 탐색한다. 간선 비용이 동일한 그래프에서 최단 거리를 찾는 데 적합하다.

함께 알아야 할 개념은 다음과 같다.

- 큐: 먼저 들어온 항목을 먼저 꺼내며 탐색 순서를 유지한다.
- 방문 기록: 같은 노드를 반복 처리하거나 무방향 연결을 계속 왕복하지 않게 한다.
- 거리: 시작점에서 해당 노드까지 필요한 최소 간선 수를 기록한다.
- 경로 복원: 도착점까지의 거리뿐 아니라 실제 커밋 나열을 출력하기 위해, 어떤 경로로 도달했는지 추적한다.

인접 관계를 바로 조회하고 큐 연산을 효율적으로 처리한다면 일반 BFS 탐색은 O(V + E)다. 경로를 문자열로 만들거나 동률 후보를 비교하는 추가 비용은 별도로 살펴봐야 한다.

### 최단 거리만 맞으면 충분한가

명세는 같은 최단 길이의 경로가 여러 개이면 **`hash1->hash2->...`로 만든 전체 문자열의 사전순이 가장 작은 경로**를 선택하도록 요구한다.

따라서 “BFS에서 처음 발견한 경로”가 이 규칙을 만족하는지 따로 검토해야 한다. 딕셔너리나 집합의 순회 순서가 곧 명세의 동률 처리 기준인 것은 아니다. 해시를 숫자로 비교하는 것과 경로 문자열을 사전순으로 비교하는 것도 구분해야 한다.

경로가 없을 때의 결과인 `No path`와, 입력 해시가 존재하지 않을 때의 `Unknown commit: <hash>`는 서로 다른 상황이다.

**스스로 설명해 보기:** BFS가 최단 간선 수를 보장하는 이유와, 그것만으로 사전순 규칙까지 자동으로 보장되지는 않는 이유는 무엇인가?

## 8. ANCESTORS와 도달 가능성

**근거: Subject.txt 4장 `ANCESTORS <commit_hash>`**

조상은 대상 커밋의 부모, 부모의 부모처럼 **부모 방향을 따라 도달할 수 있는 커밋**이다. 대상 커밋 자신은 조상이 아니다. 부모가 없는 커밋의 조상 목록은 비어 있다.

모든 조상을 찾는 데는 DFS나 BFS를 사용할 수 있다. DFS(Depth-First Search)는 한 방향을 깊게 따라간 뒤 다른 연결을 살피며, 스택이나 재귀 호출로 탐색 상태를 관리할 수 있다. 이 기능의 핵심은 최단 거리보다 빠짐없는 도달 노드 수집이다.

여러 부모 경로가 같은 조상에 도달할 수 있으므로 방문 기록의 역할을 이해해야 한다. DAG에 순환이 없더라도 같은 노드에 이르는 경로가 하나뿐이라는 보장은 없다.

도달 가능한 조상과 시작점을 포함한 노드 수를 Vᵣ, 그 탐색에서 확인하는 부모 간선 수를 Eᵣ라고 하면, 방문 기록을 사용하는 일반적인 탐색은 O(Vᵣ + Eᵣ)다. 명세는 조상 출력 순서를 따로 지정하지 않는다.

**스스로 설명해 보기:** `PATH`용 무방향 탐색을 조상 조회에 그대로 사용하면 왜 형제나 자식까지 결과에 섞일 수 있는가?

## 9. 직접 구현하는 정렬

**근거: Subject.txt 3장, 4장 「정렬 알고리즘 직접 구현」 및 `LOG --sort-by=date|author`, 7장**

정렬은 비교 기준에 따라 원소를 재배치하는 과정이다. 이 과제에서는 같은 커밋 목록에 대해 `timestamp` 기준과 `author` 기준을 적용할 수 있어야 한다.

**정렬 절차**와 **비교 기준**을 나누어 생각하면, 알고리즘 전체를 날짜용·작성자용으로 각각 복제하지 않고 기준을 바꾸는 구조를 설계할 수 있다. 구체적인 함수 형태는 구현 단계에서 다룬다.

### 이번 구현에서 사용할 방법

이번 학습에서는 **삽입 정렬**을 선택한다. 앞쪽에 이미 정렬된 구간을 유지하면서 다음 원소를 알맞은 위치에 넣는 방식이다. 명세는 특정 정렬 알고리즘이나 O(n log n) 성능을 강제하지 않는다. 평균·최악 시간복잡도와 안정성을 설명할 수 있어야 한다.

날짜와 작성자는 모두 오름차순으로 정렬하고, 비교값이 같은 커밋끼리는 입력 순서를 유지하는 방향으로 구현한다. 이는 명세가 자유롭게 둔 정렬 방향·동률 처리에 대한 구현 선택이며 CHECK.md D4에 기록한다.

### 구현 연습 1: 정렬 기준값을 꺼내기

정렬할 대상은 Commit 객체다. 그러나 두 객체 중 무엇을 먼저 놓을지 비교하려면 객체의 어떤 속성을 사용할지 정해야 한다. 이때 꺼내는 값을 **정렬 기준값 또는 정렬 키(sort key)**라고 부른다.

딕셔너리에서 객체를 찾는 키인 커밋 ID와는 역할이 다르다.

| 용도 | 기준으로 쓰는 값 |
| --- | --- |
| 커밋 저장소에서 객체 조회 | 커밋 ID인 `commit.hash` |
| 날짜순 정렬 | 생성 시각인 `commit.timestamp` |
| 작성자순 정렬 | 작성자 이름인 `commit.author` |

`sorting.py`에 다음 함수의 틀을 두고, 비교 기준을 선택하는 부분부터 구현한다.

```python
from datetime import datetime
from commit import Commit


def get_sort_key(commit: Commit, sort_by: str) -> datetime | str:
    """정렬 기준에 따라 커밋의 생성 시각 또는 작성자 이름을 반환한다."""
    pass
```

- `sort_by`가 `"date"`이면 해당 객체의 timestamp를 반환한다.
- `sort_by`가 `"author"`이면 해당 객체의 author를 반환한다.
- 지원하지 않는 기준에는 ValueError를 발생시키는 방식으로 구분한다. 정확한 내부 예외 종류는 구현 선택이다.

이 함수는 커밋을 나열하거나 옮기지 않는다. **커밋 하나에서 비교에 사용할 값 하나를 꺼내는 함수**다.

반환 타입 `datetime | str`은 한 번의 호출에서 datetime 값 또는 문자열 중 하나가 나온다는 뜻이다. 두 값을 담은 목록이나 두 값을 이어 붙인 문자열을 반환한다는 뜻은 아니다. 날짜 기준일 때 시각을 출력용 문자열로 변환하지 않고 datetime 값 그대로 사용한다.

예를 들어 Alice가 작성한 커밋의 시각이 `datetime(2026, 9, 14, 10, 30)`이라면 다음처럼 된다.

| 호출 기준 | 반환할 값 | 반환 타입 |
| --- | --- | --- |
| date | 해당 커밋의 `datetime(2026, 9, 14, 10, 30)` 값 | datetime |
| author | `"Alice"` | str |

한 번의 정렬에서는 모든 커밋에 같은 sort_by를 사용한다. 날짜 정렬 중에는 날짜끼리, 작성자 정렬 중에는 문자열끼리 비교한다. datetime과 작성자 문자열을 서로 비교하려는 것이 아니다.

### 구현 연습 2: 삽입 정렬이 원소를 옮기는 원리

다음은 숫자로 원리만 설명하는 예시다. 실제 구현에서는 숫자 대신 Commit 객체를 옮기고, 비교할 때 위 함수가 반환하는 값을 사용한다.

입력이 `[4, 1, 3]`이라고 하자. 처음 원소 하나 `[4]`만 있는 구간은 이미 정렬되어 있다고 볼 수 있다.

| 단계 | 할 일 | 리스트의 상태 |
| --- | --- | --- |
| 시작 | 앞의 한 원소는 정렬된 구간 | `[4, 1, 3]` |
| 1을 넣을 준비 | 현재 값 1을 별도 변수에 보관 | `[4, 1, 3]` |
| 4를 이동 | 4가 1보다 크므로 한 칸 오른쪽으로 이동 | `[4, 4, 3]` |
| 1 삽입 | 빈 위치에 보관했던 1을 넣음 | `[1, 4, 3]` |
| 3을 넣을 준비 | 현재 값 3을 별도 변수에 보관 | `[1, 4, 3]` |
| 4를 이동 | 4가 3보다 크므로 오른쪽으로 이동 | `[1, 4, 4]` |
| 3 삽입 | 1 뒤의 위치에 보관했던 3을 넣음 | `[1, 3, 4]` |

이동 중 같은 값이 두 번 보일 수 있지만, 삽입할 원소를 별도 변수에 보관했다가 빈 위치에 넣으므로 최종 결과에서 원소가 사라지거나 중복되지 않는다.

앞의 원소가 현재 비교값보다 **클 때만** 이동시키면, 같은 값끼리는 서로를 추월하지 않아 입력의 상대 순서가 유지된다. 이것이 이 방식에서 안정성을 지키는 조건이다.

정렬 함수는 입력 목록을 별도 리스트로 복사해서 순서를 바꾸는 방식으로 구성할 수 있다. Commit 객체의 부모·작성자·시각을 수정하는 것이 아니라, 어떤 객체를 앞에 둘지 결정하는 작업이다.

#### 원본 목록을 복사한다는 뜻

다음 두 변수의 역할을 구분한다.

| 변수 | 들어 있는 값과 타입 | 역할 |
| --- | --- | --- |
| `commits` | 호출한 쪽에서 받은 `list[Commit]` | 순서를 보존해야 하는 원본 목록 |
| `result` | `list(commits)`로 만든 새로운 `list[Commit]` | 삽입 정렬 과정에서 순서를 바꿀 결과 목록 |

`result`는 새로운 리스트지만, 그 안의 각 원소는 원본과 같은 `Commit` 객체를 가리킨다. 예를 들어 `commits[0]`과 `result[0]`은 같은 커밋 객체일 수 있다. 이것은 문제가 아니다. 정렬에서는 객체의 속성을 고치는 것이 아니라 `result` 안에서 객체가 놓인 위치만 바꾼다.

따라서 다음 두 결과를 구분해야 한다.

- `result`에서 h0와 h1의 위치를 바꿔도 `commits`의 나열 순서는 그대로다.
- `result[0].author`처럼 객체의 속성을 직접 바꾸면 같은 객체를 가리키는 원본 쪽에서도 변경이 보일 수 있다. 정렬 함수에서는 이런 속성 변경을 하지 않는다.

#### 반복문에서 사용할 값과 타입

삽입 정렬을 코드로 옮길 때는 각 변수가 무엇을 담는지 먼저 정하면 이해하기 쉽다.

| 개념상 변수 | 실제 값의 예 | 타입 | 의미 |
| --- | --- | --- | --- |
| 현재 위치 | `1`, `2`, `3` | `int` | 이번에 정렬된 구간에 넣을 원소의 인덱스 |
| 현재 커밋 | h1을 표현하는 `Commit` 객체 | `Commit` | 이동 중 사라지지 않도록 잠시 보관할 원소 |
| 현재 비교 키 | `"Alice"` 또는 특정 생성 시각 | `str` 또는 `datetime` | 현재 커밋을 어디에 넣을지 비교할 값 |
| 비교 위치 | 현재 위치보다 하나 작은 인덱스 | `int` | 정렬된 왼쪽 구간을 뒤에서부터 확인할 위치 |

여기서 h1 같은 문자열은 커밋을 조회하거나 표시할 때 쓰는 **ID**이고, 현재 커밋 변수에는 h1 문자열이 아니라 h1의 정보를 가진 **`Commit` 객체**가 들어간다. `get_sort_key()`에 전달하는 것도 ID 문자열이 아니라 `Commit` 객체다.

#### 왜 두 번째 원소부터 시작하는가

원소가 하나뿐인 구간은 비교할 상대가 없으므로 이미 정렬되어 있다고 볼 수 있다. 그래서 첫 번째 원소인 인덱스 0은 시작할 때 정렬된 구간으로 두고, 인덱스 1의 원소부터 차례로 알맞은 위치를 찾는다.

반복문은 역할이 다른 두 겹으로 생각한다.

1. 바깥 반복은 인덱스 1부터 마지막 인덱스까지 이동하며, 이번에 삽입할 `Commit` 객체를 하나 고른다.
2. 안쪽 반복은 현재 위치의 바로 왼쪽부터 거꾸로 확인하며, 현재 키보다 큰 원소를 한 칸 오른쪽으로 옮긴다.
3. 더 이상 옮길 원소가 없으면, 마지막으로 확인한 위치의 바로 오른쪽에 보관했던 현재 커밋을 넣는다.

이를 Python 문법을 채우기 전의 의사코드로 쓰면 다음과 같다.

```text
원본 커밋 목록을 결과 목록으로 복사한다

두 번째 위치부터 마지막 위치까지 반복한다
    현재 위치의 Commit 객체를 별도 변수에 보관한다
    get_sort_key로 현재 객체의 비교 키를 구한다
    비교 위치를 현재 위치의 바로 왼쪽으로 정한다

    비교 위치가 목록 안이고 왼쪽 객체의 키가 현재 키보다 큰 동안 반복한다
        왼쪽 객체를 한 칸 오른쪽 위치에 놓는다
        비교 위치를 한 칸 왼쪽으로 옮긴다

    비교 위치의 바로 오른쪽에 보관했던 현재 객체를 놓는다

결과 목록을 반환한다
```

안쪽 반복이 끝난 뒤 넣는 위치가 단순히 `비교 위치`가 아니라 **비교 위치의 바로 오른쪽**이라는 점이 중요하다. 안쪽 반복에서는 원소를 옮길 때마다 비교 위치가 이미 한 칸 왼쪽으로 이동했기 때문이다.

#### Commit 객체 세 개를 작성자순으로 옮겨 보기

다음 입력을 작성자 오름차순으로 정렬한다고 하자.

| 입력 위치 | 커밋 ID | 객체의 `author` | `get_sort_key(commit, "author")` 결과 |
| --- | --- | --- | --- |
| 0 | h0 | Zoe | `"Zoe"` |
| 1 | h1 | Alice | `"Alice"` |
| 2 | h2 | Bob | `"Bob"` |

시작할 때 `result`의 순서는 `[h0(Zoe), h1(Alice), h2(Bob)]`이다.

| 단계 | 현재 보관한 객체 | 비교 | `result`의 상태 | 설명 |
| --- | --- | --- | --- | --- |
| h1 선택 | h1(Alice) | Zoe > Alice | `[h0, h1, h2]` | h1 객체를 별도 변수에 보관한다. |
| h0 이동 | h1(Alice) | 참 | `[h0, h0, h2]` | h0를 한 칸 오른쪽에 놓는다. h1은 변수에 남아 있어 사라지지 않는다. |
| h1 삽입 | h1(Alice) | 왼쪽 끝 도달 | `[h1, h0, h2]` | 빈 것으로 생각한 인덱스 0에 h1을 놓는다. |
| h2 선택 | h2(Bob) | Zoe > Bob | `[h1, h0, h2]` | h2 객체를 별도 변수에 보관한다. |
| h0 이동 | h2(Bob) | 참 | `[h1, h0, h0]` | Zoe인 h0를 한 칸 오른쪽으로 옮긴다. |
| 왼쪽 확인 | h2(Bob) | Alice > Bob | 거짓 | h1은 옮기지 않고 안쪽 반복을 끝낸다. |
| h2 삽입 | h2(Bob) | Alice와 Zoe 사이 | `[h1, h2, h0]` | 최종 작성자 순서는 Alice, Bob, Zoe다. |

중간의 `[h0, h0, h2]`나 `[h1, h0, h0]`은 임시 상태다. 현재 삽입할 객체를 별도 변수에 보관했기 때문에 마지막 삽입까지 끝나면 누락이나 중복이 없다.

날짜 정렬도 이동 절차는 같다. 달라지는 것은 `get_sort_key()`가 작성자 문자열 대신 `datetime` 값을 반환한다는 점뿐이다. 한 번의 정렬에서 `sort_by`를 동일하게 전달하므로 문자열과 `datetime`을 서로 비교하지 않는다.

#### `>`와 `>=`는 왜 다른가

작성자가 같은 두 커밋이 입력에서 `[h1(Alice), h3(Alice)]` 순서였다고 하자. h3을 삽입할 때 왼쪽 키와 현재 키는 둘 다 `"Alice"`다.

- 이동 조건이 `왼쪽 키 > 현재 키`이면 두 값이 같을 때 이동하지 않는다. 결과에서도 h1이 h3보다 앞선다.
- 이동 조건이 `왼쪽 키 >= 현재 키`이면 같은 값인데도 h1을 오른쪽으로 옮긴다. h3이 h1을 추월하므로 입력의 상대 순서가 뒤집힐 수 있다.

이번 구현은 같은 키의 입력 순서를 유지하기로 했으므로 **더 큰 경우에만 이동**해야 한다.

#### 이번 구현 조각의 확인 질문

코드를 작성하기 전에 다음 질문에 답할 수 있으면 각 줄의 목적을 구분하기 쉽다.

1. 현재 커밋을 이동 전에 별도 변수에 보관하는 이유는 무엇인가?
2. `get_sort_key()`에는 커밋 ID와 `Commit` 객체 중 무엇을 전달하는가?
3. 바깥 반복과 안쪽 반복은 각각 무엇을 움직이는가?
4. 안쪽 반복이 끝난 뒤 현재 커밋을 왜 비교 위치의 바로 오른쪽에 넣는가?
5. 같은 키의 상대 순서를 유지하려면 왜 `>`를 사용해야 하는가?

### 평균·최악 시간복잡도

평균 시간복잡도는 입력에 관한 가정 아래 일반적으로 드는 비용이고, 최악 시간복잡도는 가장 불리한 입력에서 드는 비용이다. 실제 측정 시간과는 구분된다.

다음은 선택 가능한 정렬 알고리즘의 학습 예시다. 실제 사용할 알고리즘은 구현 단계에서 정한다.

| 알고리즘 | 핵심 생각 | 평균 | 최악 | 안정성 |
| --- | --- | --- | --- | --- |
| 삽입 정렬 | 앞쪽의 정렬된 구간에서 현재 원소가 들어갈 위치를 찾는다. | O(n²) | O(n²) | 같은 키의 원소를 서로 추월시키지 않으면 안정적이다. |
| 병합 정렬 | 목록을 나누어 각각 정렬하고 두 정렬 결과를 합친다. | O(n log n) | O(n log n) | 병합 시 키가 같으면 왼쪽 원소를 먼저 선택하는 방식으로 안정성을 유지할 수 있다. |

표는 일반적인 비교 기반 구현을 기준으로 하며, 삽입 정렬의 평균은 입력 순서가 무작위라고 보는 경우다. 역순에 가까운 입력에서는 각 원소가 앞의 많은 원소를 지나가야 한다. 최악의 경우 비교·이동 횟수는 대략 `1 + 2 + ... + (n - 1)`이 되어 n²에 비례하므로 O(n²)다. 이미 오름차순인 입력에서는 안쪽 반복이 곧 끝나지만, 바깥 반복은 각 원소를 한 번씩 확인하므로 일반적인 구현의 최선은 O(n)이다. 병합 정렬은 나누는 단계 수와 각 단계의 병합 비용을 연결해서 복잡도를 설명할 수 있어야 한다.

### 안정 정렬

안정 정렬은 **비교 키가 같은 원소끼리 입력에서의 상대 순서를 유지하는 정렬**이다. 서로 다른 키의 순서를 그대로 둔다는 뜻이 아니다.

입력에서 작성자가 같은 A와 B가 이 순서로 있었다면, 작성자 기준의 안정 정렬 후에도 A가 B보다 앞선다. 명세는 동률 처리 규칙을 자유롭게 정하도록 하므로 안정 정렬 자체가 필수 조건은 아니다. 다만 자신이 구현한 정렬이 안정적인지 설명할 수 있어야 한다.

표준 정렬 API 금지는 로그 정렬뿐 아니라 다른 기능에서 정렬이 필요할 때도 적용된다. 예를 들어 경로 동률 처리에 정렬을 사용하더라도 `sorted()`에 맡길 수 없다.

**스스로 설명해 보기:** 선택한 알고리즘의 평균·최악 복잡도는 무엇이며, 코드에서 어떤 비교 조건이 안정성에 영향을 주는가?

### 정렬 결과를 LOG 출력과 연결하기

정렬 알고리즘과 로그 문자열 생성은 맡은 역할과 입출력 타입이 다르다.

| 단계 | 값의 예 | 타입 | 역할 |
| --- | --- | --- | --- |
| 저장소의 전체 커밋 | `{"h0": h0 객체, "h1": h1 객체}` | `dict[str, Commit]` | ID로 실제 커밋 객체를 찾는 원본 저장소 |
| 딕셔너리의 값 목록 | `[h0 객체, h1 객체]` | `list[Commit]` | 삽입 정렬에 전달할 입력 |
| 삽입 정렬 결과 | `[h1 객체, h0 객체]` | `list[Commit]` | 날짜 또는 작성자 기준으로 순서가 정해진 객체 목록 |
| 정렬 결과에서 꺼낸 ID | `["h1", "h0"]` | `list[str]` | `format_log()`에 전달할 출력 순서 |
| 완성된 로그 | 여러 줄의 로그 | `str` | 나중에 CLI가 화면에 출력할 문자열 |

`Repository.commits`를 그대로 순회하면 딕셔너리의 키인 ID가 나온다. 반면 `commits.values()`를 사용하면 값인 `Commit` 객체들이 나온다. `insertion_sort()`는 객체의 `timestamp`나 `author`를 읽어야 하므로 객체 목록을 받는다.

기존 `format_log()`는 `commits: dict[str, Commit]`와 `ordered_ids: list[str]`를 받는다. 기본 LOG의 `topological_order()`도 ID 목록을 반환하므로, 이 함수의 입력 계약을 정렬 기능 때문에 바꿀 필요는 없다. 정렬된 `Commit` 객체들에서 `commit.hash`를 차례로 꺼내 ID 목록으로 바꾸면 같은 출력 함수를 재사용할 수 있다.

전체 흐름은 다음과 같다.

```text
전체 커밋 딕셔너리
    → 값들만 새 목록으로 만든다
    → insertion_sort로 Commit 객체의 순서를 정한다
    → 정렬된 각 객체에서 hash를 꺼내 ID 목록을 만든다
    → format_log에 전체 딕셔너리와 ID 목록을 전달한다
    → 로그 문자열을 반환한다
```

이 연결을 `main.py`의 작은 함수로 분리하면 나중에 CLI의 `LOG --sort-by=...` 처리는 그 함수를 호출하고 문자열을 출력하는 역할만 맡을 수 있다. 함수 이름은 구현 선택이지만, 예를 들어 다음 계약을 사용할 수 있다.

```python
def format_sorted_log(
    commits: dict[str, Commit],
    sort_by: str,
) -> str:
    """전체 커밋을 지정한 기준으로 정렬해 로그 문자열로 구성한다."""
    pass
```

이 함수 안에서는 새로운 정렬 알고리즘을 작성하지 않는다. 기존 `insertion_sort()`와 `format_log()` 사이에서 입력과 결과 타입을 맞추는 연결만 담당한다. 빈 저장소에서는 객체 목록과 ID 목록이 모두 빈 목록이 되고, 기존 `format_log()`의 계약에 따라 빈 문자열이 반환된다.

## 10. 역색인과 검색

**근거: Subject.txt 3장 및 4장 「역색인」·`COMMIT`·`SEARCH`**

일반적인 커밋 저장소는 커밋 ID로 메시지를 찾는다. **역색인(Inverted Index)**은 반대로 키워드나 작성자로 관련 커밋 ID들을 찾게 한다.

명세가 요구하는 두 연결은 다음과 같다.

```text
keyword → commit_hash 목록
author  → commit_hash 목록
```

예를 들어 A의 메시지가 `Add login feature`, B의 메시지가 `Fix login`이고 두 작성자가 Alice라면, 키워드 `login`은 A와 B에 연결되고 작성자 `Alice`도 A와 B에 연결된다.

### 토큰화와 정규화

- 토큰화: 메시지를 공백 기준으로 분리한다. 위 A 메시지에서는 `Add`, `login`, `feature`가 나온다.
- 정규화: 각 토큰을 소문자로 바꾼다. `Add`는 `add`로 저장된다.
- 색인 갱신: 새 커밋을 만들 때 작성자와 메시지 토큰에 해당 커밋 ID를 연결한다.

명세의 최소 추출 규칙은 `split`과 `lower`다. 구두점 제거, 어간 추출, 유사어 검색 등은 요구되지 않는다. 예를 들어 이 규칙만 적용하면 `login`과 `login,`은 다른 토큰이다.

검색 키워드에도 저장 시와 일치하는 정규화가 필요하다는 점을 생각해야 한다. 다만 메시지 토큰에 대한 소문자 규칙을 작성자나 브랜치 이름에까지 자동으로 확대하면 안 된다. 명령어의 대소문자 무시 규칙도 인자 전체를 소문자로 바꾸라는 뜻은 아니다.

따라서 이번 구현에서 작성자 검색은 저장된 이름과 정확히 같은 문자열을 찾는다.
예를 들어 작성자 `Alice`는 `SEARCH --author=Alice`로 찾으며, `alice`로 자동
변환하지 않는다. 명세에서 대소문자를 무시하라고 한 대상은 `SEARCH` 같은
명령어이고, 작성자 이름 인자까지는 아니다.

같은 메시지에 `login`이 반복되어도 “일치하는 커밋 목록”과 “단어가 나온 횟수”는 다른 결과다. 색인에 연결을 저장하는 방식이 검색 결과에 중복 커밋을 만들지 않는지 생각해 볼 필요가 있다.

### 이번 구현의 SEARCH 일치 규칙

`Subject.txt`는 커밋 메시지를 공백으로 나누고(`split`) 소문자로 바꾼
토큰을 역색인에 저장하도록 요구한다. `evaluate.txt`도 키워드 검색이
역색인을 이용하는지는 평가하지만, 부분 문자열 검색이나 정확한 구문 검색은
요구하지 않는다. 따라서 이번 구현은 색인의 형태에 맞춰 다음처럼 동작한다.

1. 검색어도 `lower().split()`으로 정규화한다.
2. 한 토큰 검색은 그 토큰과 정확히 같은 색인 키를 조회한다.
3. 여러 토큰 검색은 각 토큰에 연결된 커밋 ID 집합의 **교집합**을 구한다.

예를 들어 색인이 다음과 같다고 하자.

```text
"login"   -> {"h1", "h2"}
"feature" -> {"h1", "h3"}
```

검색어가 `"login feature"`라면 프로그램이 받는 값은 공백이 든 문자열
하나다. 이것을 나누면 `['login', 'feature']`가 되고, 두 ID 집합의
교집합은 `{'h1'}`이다. 따라서 두 단어를 모두 포함한 `h1`만 결과가 된다.

```text
{"h1", "h2"} ∩ {"h1", "h3"} = {"h1"}
```

여기서 “모두 포함”은 단어의 순서나 서로 붙어 있는지를 검사하는 정확한
구문 검색이 아니다. `feature ... login`처럼 떨어져 있어도 두 토큰이 모두
색인되어 있으면 결과에 포함된다. 정확한 구문 검색에는 메시지 원문을 다시
검사하거나 토큰 위치까지 저장하는 별도 색인이 필요하지만, 그 기능은 명세에 없다.

또한 토큰 전체가 같을 때만 일치한다. 따라서 `SEARCH log`는 `login`을
찾지 않는다. `log`와 `login`은 서로 다른 딕셔너리 키이기 때문이다.
대문자 차이는 소문자화로 없어지므로 `SEARCH LOGIN`은 `login`을 찾는다.

여러 토큰의 교집합을 구할 때는 첫 번째 색인 결과를 **새 집합으로 복사**해
작업 결과로 사용해야 한다. 현재 `find_by_keyword()`가 색인 내부의 `set` 객체를
그대로 반환하므로, 그 집합에 `&=` 연산을 하면 원본 색인까지 줄어들 수 있다.

```python
# result와 keyword_index['login']은 서로 다른 set 객체다.
result = set(self.find_by_keyword('login'))
result &= self.find_by_keyword('feature')
```

예를 들어 원래 `login -> {'h1', 'h2'}`였는데 복사하지 않고 `feature` 집합과
교집합을 저장하면, 검색 한 번 때문에 원본 `login` 색인이 `{'h1'}`로 바뀔 수
있다. 검색은 저장된 색인을 읽기만 해야 하므로 작업용 집합을 분리한다.

### 커밋 ID 집합을 Commit 객체 목록으로 연결하기

역색인의 값은 `Commit` 객체가 아니라 커밋 ID 문자열이다. 예를 들어 검색
결과 `{'CI_0', 'CI_2'}`의 타입은 `set[str]`이다. 반면 화면에 메시지·작성자·
시각을 출력하려면 `Commit` 객체가 필요하다.

`Repository.commits`는 `dict[str, Commit]`이므로 각 ID를 키로 사용해 객체를
조회할 수 있다.

```text
matched_ids: set[str]
    {'CI_0', 'CI_2'}
          │ 각 ID로 get_commit() 호출
          ▼
matched_commits: list[Commit]
    [Commit(CI_0), Commit(CI_2)]
```

이 과정은 저장소의 모든 커밋을 순회하는 것이 아니다. 색인이 찾아 준 결과가
`k`개라면 그 `k`개의 ID만 조회한다. 집합은 출력 순서를 보장하지 않으며,
SEARCH 결과 순서는 명세가 따로 지정하지 않았다.

### 전체 순회보다 왜 빠른가

전체 순회 검색은 매번 모든 커밋의 메시지나 작성자를 확인한다. 커밋이 V개이면 적어도 V개 항목을 살피고, 메시지 검사 비용까지 든다.

해시맵 기반 역색인의 단일 키 조회는 평균 O(1)에 후보 목록을 찾을 수 있다. 결과가 k개이면 커밋 조회와 출력에 O(k)가 더 들므로, **조회와 결과 나열을 합쳐 평균 O(1 + k)**로 설명할 수 있다. 여기서는 키와 개별 결과의 문자열 길이에 따른 비용을 별도로 둔다.

이 속도는 준비 비용을 없앤 결과가 아니다. 커밋 생성 시 메시지 토큰을 추출하고 인덱스를 갱신하는 시간과, 키워드·작성자별 연결을 보관하는 추가 메모리가 필요하다. 검색마다 모든 커밋을 읽어서 역색인을 새로 만들면 명세가 요구한 이점을 얻을 수 없다.

### 갱신 시점과 데이터의 일치 (평가 2-3)

명세의 갱신 시점은 **커밋 생성 시**다. 성공한 `COMMIT` 다음에 곧바로 `SEARCH`를 실행해도 새 커밋을 찾을 수 있어야 한다. 자신의 설계를 설명할 때는 다음 정보의 연결을 짚어 본다.

- 새 커밋의 고유 ID와 작성자·메시지를 확정하고 커밋 저장소에 등록하는 부분
- 작성자를 키로 삼아 그 커밋 ID를 연결하는 부분
- 메시지에서 소문자 토큰을 추출해 각 키워드에 같은 커밋 ID를 연결하는 부분

커밋만 저장하고 색인을 빠뜨리면 검색 결과에서 누락된다. 반대로 존재하지 않는 커밋 ID가 색인에 들어가면 결과를 조회할 수 없다. 평가에서는 이런 연결이 한 번의 커밋 생성 과정에서 어디서 이루어지는지 자신의 코드로 설명하면 된다. 트랜잭션 시스템 같은 별도의 기능을 추가하라는 뜻은 아니다.

**스스로 설명해 보기:** 결과가 모든 커밋에 해당한다면 역색인이 있어도 출력 비용이 O(V)가 될 수 있는 이유는 무엇인가?

## 11. REPL, 명령 파싱, 책임 분리

**근거: Subject.txt 2장 「CLI 인터페이스」, 4장 「CLI 공통 규칙」, 7장 「구조/품질」**

**REPL(Read–Eval–Print Loop)**은 입력을 읽고, 해석·실행하고, 결과를 출력하는 과정을 반복하는 구조다. 이 과제에서는 `mini-git>` 프롬프트에서 명령을 받으며 `exit` 또는 `quit`로 종료한다.

파싱은 입력 문자열을 명령어, 인자, 옵션으로 구분하는 과정이다. 다음 입력에서는 메시지 전체가 하나의 인자여야 한다.

```text
COMMIT "Add login feature"
```

입력 전체에 단순 공백 분리만 적용하면 따옴표 안의 공백까지 나뉜다. **명령행을 파싱하는 규칙**과 **커밋 메시지에서 검색 토큰을 추출하는 규칙**은 서로 다르다는 점을 이해해야 한다.

### 구현 연습: 명령행 한 줄을 토큰으로 나누기

Python 표준 라이브러리의 `shlex.split()`은 따옴표 안의 공백을 보존하면서
명령행을 문자열 목록으로 나눈다. 따옴표 문자는 인자를 묶는 문법이므로 결과
문자열에는 남지 않는다.

| 입력 `line: str` | `shlex.split(line)` 결과 `list[str]` |
| --- | --- |
| `init "Alice Kim"` | `['init', 'Alice Kim']` |
| `CoMmIt "Add login feature"` | `['CoMmIt', 'Add login feature']` |
| `SEARCH --author="Alice Kim"` | `['SEARCH', '--author=Alice Kim']` |
| 공백만 있는 입력 | `[]` |

명령어의 대소문자만 무시해야 하므로 결과가 비어 있지 않다면 첫 원소만
`upper()`로 바꾼다. 예를 들어 `['CoMmIt', 'Add Login']`은
`['COMMIT', 'Add Login']`이 된다. 메시지 `Add Login`까지 대문자나 소문자로
바꾸면 원문 보존 요구를 어기므로 나머지 원소는 그대로 둔다.

닫히지 않은 따옴표가 들어오면 `shlex.split()`은 `ValueError`를 발생시킨다.
첫 파싱 함수에서는 이 오류를 숨기지 않고 전달하고, 이후 REPL 오류 처리에서
잡아 `Invalid args`를 출력한 뒤 다음 입력을 받도록 연결할 수 있다.

옵션 형태는 `SEARCH --author=<name>`과 `LOG --sort-by=date|author`다. 여기서 `date|author`는 허용 값 두 개를 뜻하며, 실제로는 `--sort-by=date` 또는 `--sort-by=author`를 입력한다.

`SEARCH --author="Alice Kim"`을 `shlex.split()`으로 나누면 두 번째 토큰은
`'--author=Alice Kim'`이다. 이 문자열에서 `--author=`는 옵션 종류를 나타내는
접두사이고, 그 뒤의 `Alice Kim`이 실제 작성자 이름이다.

```text
option: '--author=Alice Kim'  (str)
         └─ 접두사 ─┘└ 이름 ┘
                       ↓
author: 'Alice Kim'           (str)
```

먼저 `startswith('--author=')`로 정확한 접두사인지 확인한 다음,
`len('--author=')` 위치부터 문자열을 잘라 이름을 얻을 수 있다. 접두사가
다르거나 뒤의 이름이 비어 있으면 내부 함수에서는 `ValueError`로 거부한다.
작성자 이름은 검색 색인의 키와 같아야 하므로 `lower()`나 `upper()`를 적용하지
않고 원문 그대로 반환한다.

이때 내부 `ValueError`의 메시지는 한국어여도 된다. `Subject.txt`의 에러 메시지
표준화 규칙은 CLI에서 사용자에게 보여 주는 안내에 적용한다. 이후 명령 실행·
REPL 계층에서 옵션 파싱의 `ValueError`를 잡아 `Invalid args`처럼 일관된 문구를
출력하면 된다. 내부 예외 문구와 최종 CLI 출력 문구를 같은 것으로 간주하지 않는다.

`LOG --sort-by=date`도 같은 접두사 추출 방식을 사용한다. 파싱 후 두 번째
토큰 `--sort-by=date`에서 접두사 `--sort-by=` 뒤를 잘라 `date`를 얻는다.
작성자 옵션과 다른 점은 자유로운 이름을 받는 것이 아니라 허용 값이 두 개로
제한된다는 점이다.

```text
option: '--sort-by=date'       (str)
                     ↓ 접두사 뒤 추출
sort_by: 'date'                (str)
allowed: {'date', 'author'}    (set[str])
```

추출한 `sort_by`가 `date` 또는 `author`이면 반환하고, 빈 값·다른 값·잘못된
접두사는 `ValueError`로 거부한다. 예를 들어 `--sort-by=message`,
`--sort-by=`, `--sort=date`는 명세에 없는 형식이다. 명령어의 대소문자 무시를
옵션 값에 확대하지 않으므로 `--sort-by=DATE`도 거부한다.

### 명령별 인자 개수 검사

`parse_command_line()`의 결과에서 첫 원소는 명령어이고 나머지는 인자다.
따라서 실제 인자 개수는 `len(parts) - 1`로 구할 수 있다.

| 명령어 | 허용 인자 개수 | 유효한 토큰 목록 예시 |
| --- | ---: | --- |
| `INIT`, `BRANCH`, `SWITCH`, `COMMIT`, `ANCESTORS` | 1 | `['INIT', 'Alice']` |
| `PATH` | 2 | `['PATH', 'CI_0', 'CI_2']` |
| `LOG` | 0 또는 1 | `['LOG']`, `['LOG', '--sort-by=date']` |
| `SEARCH` | 1 | `['SEARCH', 'login feature']` |
| `EXIT`, `QUIT` | 0 | `['EXIT']` |

이 관계는 `dict[str, set[int]]`로 표현할 수 있다. 딕셔너리의 키는 명령어
문자열이고 값은 그 명령어가 허용하는 인자 개수의 집합이다. 예를 들어
`'LOG': {0, 1}`은 LOG가 옵션 없이 실행되거나 옵션 하나를 받을 수 있다는 뜻이다.

공백을 포함한 검색어를 따옴표로 감싸면 `shlex.split()` 결과에서 문자열 하나가
되므로 SEARCH의 인자 개수는 1이다. 반대로 `SEARCH login feature`처럼 따옴표를
빼면 인자가 2개가 되어 이 검사에서 잘못된 입력으로 거부된다.

빈 토큰 목록 `[]`은 사용자가 빈 줄을 입력한 상태이므로 검사할 명령이 없다.
이 경우 예외를 발생시키지 않고 반환해 REPL이 다음 입력을 받게 한다. 명령어가
딕셔너리에 없거나 실제 인자 개수가 허용 집합에 없으면 내부 `ValueError`를
발생시키고, CLI 계층에서 일관된 입력 오류 안내로 바꾼다.

### 명령 실행 연결의 시작: INIT

파싱과 인자 검사가 끝난 `parts`를 실제 저장소 기능에 연결하는 함수는
`Repository` 객체와 토큰 목록을 입력받는다. 함수가 직접 `print()`하기보다
출력용 문자열을 반환하면 REPL 없이도 결과를 확인하기 쉽고, REPL은 나중에
그 문자열을 출력하는 책임만 맡을 수 있다.

```text
parts: ['INIT', 'Alice']       list[str]
repository: Repository 객체
             ↓ execute_command()
repository.initialize('Alice')
             ↓
result: 초기화 결과 문자열     str
```

`parts[0]`은 명령어 `INIT`, `parts[1]`은 사용자 이름 `Alice`다. 사용자 이름이
빈 문자열이거나 공백뿐이면 `INIT <user_name>`의 실제 값이 없으므로 `ValueError`로
거부한다. 유효하면 기존 `Repository.initialize()`를 호출한다.

초기화 전후 저장소 상태는 다음과 같다.

| 속성 | 호출 전 | `initialize('Alice')` 호출 후 |
| --- | --- | --- |
| `repository.branches` | `{}` | `{'main': None}` |
| `repository.head` | `None` | `'main'` |
| `repository.current_user` | `None` | `'Alice'` |

성공 결과 문자열에는 명세가 식별하도록 요구하는 현재 브랜치와 사용자를 넣는다.
Subject.txt의 결과 예시는 참고 문구이므로 똑같이 복사할 필요는 없지만, 예를 들어
`Initialized repository.`, `Current branch: main`, `Current user: Alice`를 줄바꿈으로
연결할 수 있다. 반복 INIT은 기존 `Repository.initialize()`가 `ValueError`로
거부하므로 실행 함수에서 같은 상태 검사를 다시 작성하지 않는다.

명령 실행 함수를 단계적으로 만드는 동안 아직 연결하지 않은 유효 명령에는 임시로
`NotImplementedError`를 사용한다. 이것은 최종 CLI 동작이 아니며 모든 명령 연결이
끝나면 남아 있지 않아야 한다.

### BRANCH와 SWITCH 연결

두 명령은 모두 `parts[1]`에서 브랜치 이름 문자열을 꺼내지만 변경하는 상태가
다르다. `execute_command()`가 `repository.branches`나 `repository.head`를 직접
바꾸지 않고 기존 Repository 메서드를 호출해야 이 규칙이 한곳에 유지된다.

```text
BRANCH feature
→ repository.create_branch('feature')
→ 현재 HEAD 커밋을 가리키는 feature 항목 추가
→ 현재 repository.head는 바뀌지 않음

SWITCH feature
→ repository.switch_branch('feature')
→ repository.head만 'feature'로 변경
→ 커밋이나 브랜치 위치는 바뀌지 않음
```

예를 들어 main이 `CI_0`을 가리키는 상태에서 BRANCH를 실행하면 다음과 같다.

| 시점 | `branches` | `head` |
| --- | --- | --- |
| 실행 전 | `{'main': 'CI_0'}` | `'main'` |
| `BRANCH feature` 후 | `{'main': 'CI_0', 'feature': 'CI_0'}` | `'main'` |
| `SWITCH feature` 후 | 동일 | `'feature'` |

두 명령의 이름이 빈 문자열이나 공백뿐이면 `ValueError`로 거부한다. 성공 결과는
각각 `Created branch: feature`, `Switched to branch: feature`처럼 대상 이름을
포함한 문자열로 반환할 수 있다. 중복 생성·초기화 전 실행·없는 브랜치 전환은
Repository 메서드가 상태 변경 전에 `ValueError`로 거부하므로 같은 검사를
명령 실행 함수에 다시 작성할 필요는 없다. 사용자에게 보여 줄 최종 오류 문구에
대상 브랜치 이름을 넣는 작업은 REPL 오류 처리 단계에서 연결한다.

### COMMIT 연결

파싱된 `COMMIT "Add login feature"`는 `['COMMIT', 'Add login feature']`가
된다. `parts[1]`은 메시지 원문이며, 검색 키워드처럼 다시 토큰으로 나누거나
소문자로 바꾸지 않는다. 빈 문자열이나 공백뿐인 메시지는 실제 내용이 없으므로
명령 실행 단계에서 `ValueError`로 거부한다.

```text
message: 'Add login feature'   str
              ↓ repository.create_commit(message)
new_commit: Commit 객체
              ├─ hash: 'CI_0'          str
              ├─ message: 원문          str
              ├─ author: 현재 사용자    str
              └─ parents: 부모 ID 목록  list[str]
```

`Repository.create_commit()`은 ID 생성, 부모 결정, 저장, 현재 브랜치 이동,
작성자·키워드 색인 갱신까지 이미 담당한다. `execute_command()`은 이 상태 변경을
직접 반복하지 않고 메서드를 한 번 호출한 뒤 반환된 `Commit` 객체의 값을 출력용
문자열에 연결한다.

명세 예시 `[main CI_0] Initial commit`처럼 현재 브랜치 이름,
`new_commit.hash`, `new_commit.message`를 식별할 수 있게 반환하면 된다. 초기화 전
COMMIT은 `Repository.create_commit()`이 상태 변경 없이 `ValueError`로 거부한다.
성공한 뒤에는 `repository.branches[repository.head]`, 저장소 딕셔너리의 키,
두 역색인이 모두 같은 새 커밋 ID를 가리켜야 한다.

입력 개수나 옵션 형식이 잘못된 상황과, 형식은 맞지만 대상 브랜치·커밋이 없는 상황을 구분한다. 명세는 최소 에러 메시지의 예로 `Invalid args`, `Unknown branch: <name>`, `Unknown commit: <hash>`를 제시한다.

탐색·정렬·인덱싱을 독립된 함수 또는 클래스로 나누면, 입력을 읽는 과정과 알고리즘이 결과를 만드는 과정을 구분해서 설명할 수 있다. 엔트리 포인트 1개라는 제출 조건이 모든 로직을 한 함수에 넣으라는 뜻은 아니다. 특정 클래스 수나 파일 수는 명세에서 정하지 않는다.

### 그래프 로직을 재사용한다는 뜻 (평가 2-4)

그래프 접근과 알고리즘의 입출력을 CLI로부터 분리하면 같은 함수를 REPL 외부에서도 호출해 결과를 확인할 수 있다. 커밋 조회나 부모 관계 조회처럼 의미가 같은 부분은 공유할 수 있다.

다만 `LOG`는 부모 우선 순서, `PATH`는 무방향 최단 경로, `ANCESTORS`는 부모 방향의 도달 가능성을 다룬다. 재사용을 위해 세 기능을 무조건 같은 BFS 함수에 넣으면 목적이 다른 부분까지 섞일 수 있다. 무엇을 공유하고 무엇을 각 알고리즘의 책임으로 남겼는지 설명하는 것이 핵심이다. 이를 위해 별도의 범용 그래프 프레임워크를 만들 필요는 없다.

### 주석과 docstring의 작성 기준 (평가 2-5)

주요 함수·클래스에는 그 역할과 사용 규칙을 설명한다. 구체적으로 입력·반환값, 변경하는 상태가 있는지, 알고리즘이 사용하는 방향이나 비교 기준을 살필 수 있다.

예를 들어 경로 탐색에는 “무방향 연결에서 간선 수가 최소인 경로를 찾는다”는 설명이 중요하다. 커밋 생성에는 커밋 저장소·현재 브랜치·역색인 중 무엇이 갱신되는지 드러나야 한다. 주석은 코드 한 줄을 그대로 한국어로 반복하기보다, 방문 기록이나 동률 처리처럼 이유를 알아야 하는 선택을 설명하는 데 쓸 수 있다.

이 항목들은 문서를 작성하는 판단 기준이며, 명세가 정하지 않은 고정된 docstring 형식을 요구하는 것은 아니다.

**스스로 설명해 보기:** `COMMIT`이라는 명령어의 대소문자를 무시하면서 메시지 원문은 보존하려면, 입력의 어느 부분에 어떤 처리를 해야 하는가?

## 12. 명세에서 확정하지 않은 부분

다음은 구현 결정을 내리기 전에 명세의 범위를 구분하기 위한 메모다. 추가 기능 요구나 확정된 동작으로 취급하지 않는다. 명백한 모순으로 판단되는 경우에는 사용자와 의논한 뒤 방향을 정한다.

| 항목 | 명세에서 확인되는 내용 | 아직 확정하지 않은 해석 |
| --- | --- | --- |
| 공백이 포함된 검색어 | 검색 키워드에 공백을 허용하며, 색인은 공백으로 나눈 소문자 토큰을 저장한다. | 이번 구현은 검색어도 토큰화하고 각 토큰의 ID 집합을 교집합으로 합치는 AND 검색으로 결정했다. 토큰 위치를 확인하는 구문 검색과 OR 검색은 추가하지 않는다. |
| 키워드의 “포함” 의미 | 토큰 기반 역색인과 “키워드가 포함된 커밋 메시지”를 요구한다. | 이번 구현은 소문자화된 토큰 전체 일치로 결정했다. 따라서 `log`는 `login`에 일치하지 않는다. |
| 기본 LOG와 정렬 옵션 | 기본 `LOG`에는 부모 우선 규칙이 있고, 옵션에는 날짜·작성자 정렬 규칙이 있다. 평가 4-3은 작성자 정렬에 부모 우선 조건을 더하는 상황을 가정한다. | 평가지 문구는 기존 작성자 정렬에는 부모 우선 조건을 추가하지 않는 해석을 뒷받침한다. 강화된 조건은 응용 질문으로 다룬다. |
| LOG가 조회할 커밋의 범위 | 결과 예시에는 현재 브랜치와 다른 브랜치의 커밋이 함께 나온다. | 기능 본문은 조회 범위를 별도로 정의하지 않는다. 예시는 저장소 전체 로그를 시사하지만, 실제 Git의 기본 로그 범위를 그대로 가져오면 안 된다. |
| 날짜·작성자 정렬 방향 | 각각 timestamp와 작성자 이름을 기준으로 하며 동률 처리는 자유다. | 오름차순·내림차순은 명시하지 않는다. 구현할 때 선택할 사항이다. |
| 초기화 및 빈 상태 | `INIT`은 저장소·main·HEAD·현재 사용자를 설정한다. 커밋은 부모 0개 이상을 허용한다. | 반복 `INIT`의 처리나 커밋이 없는 상태에서의 일부 명령 동작은 세부적으로 지정하지 않는다. 별도의 사용자 변경 명령도 요구하지 않는다. |

기능을 구현할 때는 **명시된 요구사항**, **학습을 위한 구현 선택**, **해석이 필요한 부분**을 구분해서 검토한다.

## 14. 조건 변경을 가정한 응용 질문

**근거: evaluate.txt 항목 4**

아래는 평가에서 제시한 가정에 대한 학습이다. 현재 `PATH`를 방향 그래프로 바꾸거나, 정렬 기능·해시 생성 방식을 더 추가하는 구현 지시가 아니다.

### 평가 4-1. 커밋 수가 10배 늘면 어디가 병목이 되는가

먼저 입력 크기의 의미를 정해야 한다. V는 커밋 수, E는 부모 연결 수, k는 검색 결과 수다. 커밋당 부모 수와 메시지 길이가 비슷하게 유지된다면 V가 10배일 때 E와 전체 메시지 분량도 대략 10배가 된다. 그래프 연결 밀도나 메시지 길이까지 크게 변하면 예측은 달라진다.

| 처리 방식 | 크기가 10배일 때 예상되는 연산량 변화 | 설명할 수 있는 개선 방향 |
| --- | --- | --- |
| 해시맵으로 커밋 1개 조회 | 평균 O(1)이므로 V 때문에 조회 횟수가 10배로 늘지는 않는다. 저장 메모리는 증가한다. | 조회 시 해시맵을 사용하는지 확인한다. |
| 전체 커밋을 훑는 검색 | 메시지 길이가 비슷하면 대략 10배 | 이미 요구된 역색인으로 후보를 직접 조회한다. 결과 k개를 출력하는 비용은 남는다. |
| 인접 관계를 이용한 BFS·DFS·위상 정렬 | O(V + E)이므로 위 가정에서 대략 10배 | 각 노드·간선의 반복 처리를 피하고, 필요한 인접 관계를 바로 조회한다. |
| 방문 노드마다 전체 커밋을 훑어 자식 찾기 | V개 노드 각각에서 V개를 확인하면 O(V²), 대략 100배 | 탐색에 필요한 양방향 인접 관계 등을 준비하는 비용과 반복 순회의 비용을 비교한다. |
| O(V²) 정렬 | 대략 100배 | 입력 규모에 따라 O(V log V) 정렬을 선택하는 이유를 설명한다. |
| O(V log V) 정렬 | 약 `10 × log(10V) / log(V)`배 | 단순히 항상 10배라고 하지 않고 로그 항의 증가도 고려한다. |
| 로그·검색 결과 출력 | 결과 수가 10배이면 비슷한 길이의 출력도 대략 10배 | 모든 결과를 출력해야 한다면 그 비용 자체를 없앨 수는 없다. |

자료구조의 작은 연산도 살펴야 한다. 예를 들어 Python 리스트의 맨 앞 원소를 삭제하면 뒤 원소들을 이동시켜야 하므로, BFS에서 반복하면 큐 처리 비용이 커질 수 있다. 큐를 어떤 방식으로 관리해야 불필요한 이동을 피할 수 있는지 설명해 본다.

개선 방향은 자신이 선택한 구현에서 실제로 발생하는 반복 작업을 근거로 말한다. 이 질문은 벤치마크 명령이나 캐시 같은 새 기능을 필수로 요구하지 않는다. `PATH`의 사전순 후보 비교 비용도 일반 BFS 비용과 별도로 고려해야 한다.

### 평가 4-2. PATH에서 부모 방향만 허용하면 무엇이 달라지는가

3절의 예시에서 B와 C는 모두 A의 자식이다. 현재 요구사항에서는 연결을 무방향으로 보므로 B에서 C까지 `B → A → C`로 이동할 수 있다.

부모 방향만 허용한다는 가정에서는 B → A는 가능하지만 A → C는 불가능하다. 따라서 B에서 C로는 경로가 없고, B에서 A로는 길이 1의 경로가 있다. A에서 B로는 갈 수 없으므로 경로 존재 여부도 더 이상 대칭적이지 않다.

구현에서 바뀌는 핵심은 **현재 노드에서 다음으로 이동할 수 있는 이웃의 정의**다. 부모와 자식을 모두 후보로 삼던 부분에서 부모만 후보로 삼게 된다. 모든 간선의 비용이 여전히 1이므로 BFS를 최단 경로 탐색에 계속 사용할 수 있다. 최단 경로 동률 규칙 등 바뀌지 않은 요구는 그대로 고려한다.

### 평가 4-3. 작성자 정렬에 부모 우선 조건도 더한다면

먼저 두 조건이 항상 함께 성립할 수 있는지 살핀다. 부모 P의 작성자가 Zoe이고 자식 C의 작성자가 Alice라고 하자. 작성자 오름차순만 보면 C가 먼저지만, 부모 우선 조건에서는 P가 먼저다. **전체 목록의 작성자 오름차순과 부모 우선 순서를 언제나 동시에 만족시킬 수는 없다.**

따라서 강화된 요구가 실제로 주어진다면 어떤 조건을 우선하는지 정의해야 한다. 해결 전략의 한 예는 **부모 우선 조건을 지키면서, 지금 출력 가능한 커밋들 중 작성자 순으로 선택하는 것**이다. 오름차순은 이 설명을 위한 예시이며 원래 명세에 정해진 방향은 아니다.

이 전략은 Kahn 방식과 연결된다.

1. 아직 출력되지 않은 부모가 없는 커밋들을 선택 가능한 후보로 둔다.
2. 그 후보들 사이에서 작성자 기준으로 다음 커밋을 고른다.
3. 선택한 커밋을 출력하고 자식들의 남은 부모 수를 갱신한다.
4. 모든 부모가 출력된 자식은 다음 선택 후보가 된다.

결과는 부모 관계를 만족하는 로그이며, 작성자 기준은 선택 가능한 후보 사이의 우선순위다. 위상 정렬 결과를 나중에 작성자로 전체 재정렬하면 부모 우선 조건이 다시 깨질 수 있다. 작성자가 같은 항목의 순서를 보존하는 안정 정렬만으로도 이 문제는 해결되지 않는다.

이 설명이 특정 후보 관리 자료구조나 추가 정렬 기능의 구현을 요구하는 것은 아니다. 구현한다면 표준 정렬 API 금지는 여전히 적용되며, 후보 선택에 드는 비용도 전체 복잡도에 포함해야 한다.

### 평가 4-4. 카운터와 난수 방식은 테스트·재현성·디버깅에 어떤 차이가 있는가

두 방식 모두 명세가 허용한다. 중요한 조건은 세션 안에서 커밋 ID가 중복되지 않는 것이다.

| 관점 | 카운터 기반 | 난수 기반 |
| --- | --- | --- |
| 유일성 | 같은 세션에서 사용한 번호를 재사용하지 않도록 관리하면 설명하기 쉽다. | 중복 가능성이 낮다는 것과 없다는 것은 다르다. 기존 ID 확인과 중복 시 대응이 필요하다. |
| 재현성 | 같은 시작 상태와 같은 생성 순서라면 같은 ID를 얻기 쉽다. | 같은 명령을 실행해도 ID가 달라질 수 있다. 의사난수의 생성 조건과 호출 순서를 통제하면 재현에 도움이 된다. |
| 테스트 | 예상 ID와 부모 연결을 고정된 예시로 확인하기 쉽다. | 생성된 ID를 받아 관계를 확인하거나, 테스트에서 제어 가능한 난수 공급으로 중복 상황을 만들 수 있다. |
| 디버깅 | ID로 생성 순서를 파악하기 쉬워 이력 추적에 도움이 된다. | ID만으로 생성 순서를 추정하기 어렵다. timestamp·message·parents를 함께 살펴야 한다. |

난수 생성에서 같은 seed를 사용하는 것은 의사난수 수열의 재현을 위한 수단이지 ID 중복을 막는 수단이 아니다. 중복이 실제로 나오도록 입력을 통제했을 때 기존 커밋을 덮어쓰지 않는지 설명하는 것과, 여러 번 실행해서 우연히 중복이 없었음을 확인하는 것은 다르다. 이 역시 테스트 관점을 묻는 학습이며, seed 설정 CLI 옵션을 추가하라는 요구는 아니다.

해시 문자열이 달라지면 `PATH`의 사전순 동률 결과도 달라질 수 있다. 따라서 서로 다른 ID 생성 방식의 실행 결과를 비교할 때는 최단 길이와 부모 관계뿐 아니라, 그 실행에서 생성된 실제 해시 문자열을 기준으로 동률 규칙을 확인해야 한다.
