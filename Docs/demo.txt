0. 발표 전 준비 (10분 발표 시간 밖)
================================================================
1) 현재 위치에서 Python 3.10 이상을 사용한다. 이 환경에서는 python3가 동작한다.
   셸에서 python3 --version으로 확인한다. 필요하면 실행 가능한 python3.11 등으로 바꾼다.
2) 처음 시작하는 두 터미널 T1/T2를 연다. 입력 프롬프트를 확인한다.
   운영체제 셸: cd / python3 실행 명령
   Mini Git REPL: mini-git> (D 명령)
   Python 인터프리터: >>> (준비 코드 및 B 명령)
3) T2에서 cli.txt 0단계의 준비 코드를 순서대로 한 줄씩 입력한다.
   items는 Commit 객체 목록, commits는 ID→객체 dict, index는 검증용 역색인이다.
   준비 단계에서는 store_commit/COMMIT을 실행하지 않는다. 각 객체를 직접 만들어 색인에 등록한다.
4) T1에서 cli.txt 1단계의 cd와 python3 -B main.py를 실행한다. INIT은 발표 P02에서 한다.
5) 이미지를 파일명 순서가 아닌 script.txt의 문단 안내에 맞춰 연다.
   01 구조 → 02 이력 → 03 LOG → 04 PATH → 05 색인 → 06 정렬 → 07 동률 → 08 조건 변경.
   실제 대본에서는 07 다음에 06을 다시 보여 준다.
6) 같은 세션에서 D03~D09를 반복하면 ID가 달라진다. 재시연은 exit 후 새 프로세스로 시작한다.
   명령 시연 중 실제 시각은 달라진다. SEARCH와 집합 출력의 나열 순서는 정답 조건으로 고정하지 않는다.

2. 내부 함수 검증 — B01~B06 (T2 >>>)
================================================================
이 데이터는 CHECK.md 12단계 표를 그대로 사용한다. 시각은 t0+분으로 고정했다.
ID  부모      author timestamp          message
h0  []        Zoe    2024-01-01 09:01  Initial commit
h1  [h0]      Alice  2024-01-01 09:03  Add login feature
h2  [h0]      Bob    2024-01-01 09:02  Fix login
h3  [h1,h2]   Alice  2024-01-01 09:04  Ship login login
hx  []        Evan   2024-01-01 09:00  Separate history
items와 commits의 초기 나열 순서: h0, h1, h2, h3, hx.

필수 COMMIT은 부모를 0개 또는 1개만 만든다. parents 자료형과 그래프 함수가 여러 부모를
지원하는지는 이 검증으로 보완한다. 보너스 merge를 구현했다고 설명하지 않는다.
작성자도 INIT 한 번으로 고정되므로, 다양한 작성자 정렬·검색은 이 검증 데이터를 쓴다.

[B01] 최단 경로 동률
입력 위치: T2 >>>
입력:
    print(" -> ".join(find_shortest_path(commits, "h0", "h3")))
기대:
    h0 -> h1 -> h3
설명:
    후보 h0->h1->h3과 h0->h2->h3은 모두 간선 2개다. 전체 문자열의 사전순으로 h1 경유를 고른다.

[B02] 여러 부모의 조상
입력 위치: T2 >>>
입력:
    print(find_ancestors(commits, "h3"))
기대:
    {h0, h1, h2} 집합. 출력 순서는 자유.
설명:
    두 부모에서 공통 조상 h0에 도달해도 집합으로 중복을 막는다. h3과 hx는 조상이 아니다.

[B03] 여러 부모의 로그
입력 위치: T2 >>>
입력:
    print(" -> ".join(topological_order(commits)))
기대:
    hx -> h0 -> h2 -> h1 -> h3
설명:
    처음 ready=[h0,hx]에서 끝의 hx부터 꺼낸 결과다. h3은 h1·h2 뒤에만 나온다. hx의 위치는 명세가 고정하지 않는다.

[B04] 작성자 정렬·안정성
입력 위치: T2 >>>
입력:
    print([(c.hash, c.author) for c in insertion_sort(items, "author")])
기대:
    [('h1', 'Alice'), ('h3', 'Alice'), ('h2', 'Bob'), ('hx', 'Evan'), ('h0', 'Zoe')]
설명:
    h1과 h3의 author가 같으므로 원래 h1→h3 순서를 유지한다. author 정렬이 부모 우선까지 지킬 필요는 없다.

[B05] 날짜 정렬
입력 위치: T2 >>>
입력:
    print([c.hash for c in insertion_sort(items, "date")])
기대:
    ['hx', 'h0', 'h2', 'h1', 'h3']
설명:
    날짜가 입력 순서와 다르게 섞여 있어 정렬 기준이 실제로 작동하는지 볼 수 있다.

[B06] 다른 작성자 제외
입력 위치: T2 >>>
입력:
    print(index.find_by_author("Alice"))
기대:
    {h1, h3} 집합. 출력 순서는 자유.
설명:
    Bob·Zoe·Evan의 커밋을 제외한다. 색인의 집합 순서는 자유다.

발표 후 T2에서 quit()로 종료한다. main.py REPL의 quit와 다른 Python 문법이다.

3. 추가 리허설 (cli.txt 3단계)
================================================================
- 초기화 전 log: 초기화 오류.
- INIT 후 빈 log/search: 아무 결과 줄 없이 다음 프롬프트.
- 빈 메시지와 닫히지 않은 따옴표: 오류 후 다음 명령 수용.
- Valid message만 실제 CI_0을 만든다. 실패한 COMMIT은 ID를 소비하지 않는다.
- ancestors CI_0: 루트이므로 빈 결과.
- 없는 키워드·다른 대소문자의 작성자: 빈 결과.
- 반복 INIT, main 중복 BRANCH: 오류, 기존 상태 보존.
- 빈 옵션 값, 인자 초과, unknown, exit now: 오류 후 계속 실행.
- 마지막 log에는 CI_0 하나가 남아 있고 quit로 종료한다.

EOF/Ctrl-D 종료는 현재 별도 처리하지 않는다. 이 리허설의 정상 종료는 exit/quit를 사용한다.
기본 LOG 순서, 검색 결과 집합, 오류 후 상태 보존을 기준으로 확인한다.
