# B5-2 구현 체크리스트

구현 근거는 [Subject.txt](Subject.txt)의 필수 요구사항이다. 학습 설명은 [Study.md](Study.md), 평가 문항은 [evaluate.txt](evaluate.txt)를 참고한다. 평가의 조건 변경 질문은 마지막의 설명 점검에서 다룬다.

각 단계에서는 필요한 클래스·함수의 틀을 받은 뒤 직접 세부 내용을 채운다. 구현 후에는 Git 변경점을 기준으로 검토하고, 해당 단계의 동작 확인까지 마쳤을 때 멘토가 통과한 항목을 체크한다. 아래 단계 번호는 학습을 위한 구현 순서이며 파일이나 클래스 수를 강제하지 않는다.

CLI를 연결하기 전에는 함수·객체에 작은 데이터를 직접 넣어 확인할 수 있다. 아래 확인 예시는 수동 실행이나 테스트 중 적합한 방법을 선택하면 되며, 특정 테스트 도구의 도입을 요구하지 않는다.

## 0. 구현 범위와 결정 사항

**근거: Subject.txt 2장·4장·6장·7장**

- [ ] Python 3.10 이상에서 실행할 환경을 확인한다.
- [ ] 커밋 메타데이터를 메모리에서 관리하는 범위로 구현한다. 파일 내용 추적·네트워크 통신·데이터 저장 및 복구 기능은 구현 항목에 넣지 않는다.
- [ ] 그래프 전용 라이브러리와 정렬 관련 표준 API를 사용하지 않는 제약을 확인한다. `sorted()`·`list.sort()` 금지는 로그 외의 기능에도 적용된다.

다음 표는 새로운 기능 목록이 아니라, 명세가 세부 동작을 정하지 않은 지점을 기록하는 곳이다. 관련 단계에 도달하기 전까지 필요한 사항을 결정한다. 명백한 모순이 확인되면 사용자와 의논한 뒤 정하며, 다른 단계의 학습까지 미리 멈출 필요는 없다.

| ID | 구분 / 결정할 내용 | 결정 시점 | 현재 기록 |
| --- | --- | --- | --- |
| D1 | 해석 필요: `SEARCH "login feature"`의 매칭 의미. 인자 하나로 읽는 것과 구문·여러 토큰을 매칭하는 것은 다른 문제다. | 10단계 전 | 미정. AND·OR·구문 검색을 모두 구현하는 요구로 확대하지 않는다. |
| D2 | 해석 필요: `SEARCH log`가 `login`에도 일치하는지. 토큰 역색인과 “포함”이라는 표현의 범위를 정한다. | 10단계 전 | 미정. 부분 문자열 검색을 임의로 추가하지 않는다. |
| D3 | 조회 범위: 기본·정렬 LOG에서 어떤 커밋들을 출력할지 정한다. | 7단계 전 | 결과 예시는 다른 브랜치의 커밋도 포함하므로 저장소 전체를 조회하는 해석을 기준안으로 둔다. |
| D4 | 구현 선택: 날짜·작성자 정렬의 방향과 같은 키의 처리 규칙을 정한다. | 8단계 전 | 미정. 정렬 방향은 명시되지 않았고 동률 처리는 자유다. 안정 정렬은 설명 대상이며 의무 조건은 아니다. |
| D5 | 구현 선택: 초기화 전 명령, 반복 INIT, 빈 저장소, 중복 브랜치 이름 등의 처리와 안내 문구를 정한다. | 2·5·11단계에서 관련 동작 구현 전 | 확정·검증 완료: 첫 INIT은 main·HEAD·현재 사용자를 설정한다. 반복 INIT은 사용자명이 같거나 달라도 `ValueError`로 거부하며 기존 상태를 유지한다. 초기화 전 COMMIT·BRANCH·SWITCH도 상태 변경 없이 `ValueError`로 거부한다. 초기화된 빈 저장소에서는 `None`을 가리키는 새 브랜치 생성과 전환을 허용한다. 중복 브랜치 생성과 존재하지 않는 브랜치로의 전환은 기존 상태를 유지하고 `ValueError`로 거부한다. 나머지 초기화 전 명령·빈 저장소의 다른 명령은 해당 단계에서 결정한다. |

기본 `LOG`는 부모 우선 출력, `LOG --sort-by=...`는 선택한 필드에 따른 정렬로 구분한다. 평가 4-3이 작성자 정렬에 부모 우선 조건을 추가하는 상황을 가정한다는 점을 해석 근거로 삼는다.

## 1. 커밋 표현과 ID 기반 저장·조회

**근거: Subject.txt 4장 「커밋 그래프」 / 평가 2-2**

- [x] `parents`는 부모가 없는 경우와 여러 부모가 있는 경우를 표현할 수 있게 한다.
- [x] 커밋 ID로 빠르게 조회할 수 있는 저장 구조를 만든다. 해시맵은 선택 가능한 방식이다.
- [x] 세션 안에서 중복되지 않는 ID 생성 방식을 하나 선택하고 유일성을 보장한다. 생성 후보가 중복될 수 있는 방식이라면 기존 커밋을 덮어쓰지 않도록 처리한다.

**완료 확인**

- [x] 서로 다른 커밋을 저장한 뒤 각각의 ID로 올바른 커밋을 조회한다.
- [x] 선택한 방식에서 ID가 재사용되지 않는 이유를 설명하고 확인한다. 난수를 선택했다면 중복 후보를 의도적으로 준 상황도 확인한다.

이 단계의 저장·조회는 내부 자료구조 작업이다. 별도의 커밋 등록 CLI 명령을 추가하는 것이 아니다.

- [x] 작성자 색인의 키로 해당 커밋 후보를 가져올 수 있게 한다.
- [x] 키워드 색인의 키로 해당 커밋 후보를 가져올 수 있게 한다.

**완료 확인**

- [x] 같은 작성자를 가진 여러 커밋을 모두 찾을 수 있다. 등록되지 않은 작성자나 빈 색인을 조회하면 빈 집합을 반환한다.
- [x] 같은 키워드를 가진 여러 커밋을 모두 찾을 수 있다.

이 단계는 색인의 저장과 후보 조회까지다. 공백 포함 검색어의 매칭 의미는 D1·D2를 정한 뒤 10단계에서 연결한다.

## 4. COMMIT과 상태 갱신

**근거: Subject.txt 4장 `COMMIT`·「커밋 그래프」 / 평가 1-2·2-3·3-1**

- [x] 현재 사용자를 작성자로 하고 메시지·생성 시각·고유 ID를 가진 커밋을 생성한다.
- [x] 현재 HEAD에 커밋이 없으면 부모 없이 생성하고, 있으면 그 커밋을 부모로 설정한다.
- [x] 새 커밋을 저장하고 현재 브랜치가 새 커밋을 가리키도록 갱신한다. HEAD에서 이 새 위치를 조회할 수 있어야 한다.
- [x] 커밋 생성 과정에서 3단계의 작성자·키워드 역색인 갱신을 호출한다.
- [x] 생성 동작이 기존 부모 관계를 바꾸거나 순환을 만들지 않도록 한다.

**완료 확인**

- [x] 첫 커밋 A의 부모는 없고, 다음 커밋 B의 부모는 A다.
- [x] A와 B의 ID가 다르며 메시지·작성자·시각을 확인할 수 있다.
- [x] COMMIT 성공 직후 두 색인에서 새 커밋을 조회할 수 있다.
- [x] 커밋 저장소·브랜치 위치·역색인이 같은 새 커밋 ID를 가리킨다.

## 5. BRANCH와 SWITCH

**근거: Subject.txt 4장 `BRANCH`·`SWITCH` / 평가 1-2·2-1**

- [x] `BRANCH <branch_name>`으로 현재 HEAD 커밋을 가리키는 새 브랜치를 만든다.
- [x] `SWITCH <branch_name>`으로 현재 작업 브랜치를 전환한다.
- [x] 존재하지 않는 브랜치를 구분해 에러를 전달할 수 있게 한다.
- [x] D5 중 빈 저장소에서의 브랜치 생성과 중복 이름 처리 정책을 기록하고 적용한다.

**완료 확인**

- [x] `main`에서 A를 만든 뒤 `feature`를 생성하면 두 브랜치가 같은 A를 가리키고 현재 브랜치는 `main`이다.
- [x] `feature`로 전환해 B를 생성하면 B의 부모는 A이고, `feature`만 B를 가리킨다.
- [x] `main`으로 돌아와 C를 생성하면 C의 부모는 A이고, `main`은 C, `feature`는 B를 가리킨다.
- [x] 브랜치 생성으로 기존 커밋이 복제되거나 부모 관계가 수정되지 않는다.
- [x] 브랜치 전환으로 기존 커밋이 복제되거나 부모 관계가 수정되지 않는다.

## 6. ANCESTORS — 부모 방향 탐색

**근거: Subject.txt 4장 `ANCESTORS` / 평가 1-5·2-4**

- [ ] 입력 커밋에서 부모 방향으로 도달 가능한 모든 조상을 수집한다.
- [ ] 시작 커밋 자신과 자식·형제 커밋은 조상 결과에 넣지 않는다.
- [ ] 같은 조상으로 여러 경로가 이어져도 중복 처리·출력을 피한다.
- [ ] 존재하지 않는 커밋을 빈 조상 목록과 구분해 에러로 전달한다.

**완료 확인**

- [ ] 부모가 없는 커밋의 조상 목록은 비어 있다.
- [ ] 한 줄로 연결된 이력에서 부모·부모의 부모를 모두 찾는다.
- [ ] 여러 부모가 같은 조상을 공유하는 검증용 데이터에서도 모든 조상이 한 번씩 나온다. 명세가 지정하지 않은 출력 순서는 정답 조건으로 고정하지 않는다.

## 7. 기본 LOG — 부모 우선 출력

**근거: Subject.txt 4장 `LOG` / 평가 1-3·2-4·3-2**

- [ ] D3의 조회 범위를 기록한다.
- [ ] 출력 대상의 모든 부모가 해당 자식보다 먼저 나오도록 순서를 구성한다.
- [ ] 분기나 여러 부모가 있는 그래프에서도 대상 커밋을 빠짐없이 한 번씩 출력할 수 있게 한다.
- [ ] 각 커밋의 `hash`, `author`, `timestamp`, `message`를 식별할 수 있는 출력 형태를 준비한다.

**완료 확인**

- [ ] 5단계의 A·B·C에서 A가 B와 C보다 먼저 나온다. B와 C 사이의 순서는 부모 우선 조건만으로 고정하지 않는다.
- [ ] 여러 부모가 있는 커밋은 모든 부모보다 뒤에 나온다.
- [ ] 입력 자료의 나열 순서를 바꿔도 부모 우선 조건이 유지된다. 단순 저장 순서나 시각 정렬에 기대어 통과한 것은 아닌지 확인한다.

## 8. 직접 구현하는 정렬과 LOG 옵션

**근거: Subject.txt 4장 「정렬 알고리즘 직접 구현」·`LOG --sort-by=date|author` / 평가 1-6·3-4**

- [ ] 사용할 정렬 알고리즘 하나를 선택해 직접 구현한다.
- [ ] 비교 기준을 바꿀 수 있도록 구성한다.
- [ ] D4에 정렬 방향과 동률 처리 규칙을 기록한다.
- [ ] `date`는 `timestamp`, `author`는 작성자 이름을 기준으로 정렬한다.
- [ ] 정렬된 로그에서도 `hash`, `author`, `timestamp`, `message`를 식별할 수 있다.

**완료 확인**

- [ ] 빈 목록·원소 하나·여러 원소에서 누락이나 중복 없이 정렬된다.
- [ ] 날짜가 섞인 입력과 작성자가 서로 다른 입력에서 각각 선택한 방향으로 정렬된다.
- [ ] 같은 키가 있는 입력의 결과가 정한 동률 처리 규칙과 맞는다. 안정 정렬이라고 설명한다면 원래 상대 순서가 유지되는지도 확인한다.
- [ ] 정렬 로그를 조회한 뒤에도 기본 LOG의 부모 우선 동작과 브랜치·부모 관계가 유지된다.

작성자를 바꾸는 새 CLI 명령을 만들 필요는 없다. 정렬 함수에 여러 작성자의 검증용 커밋 목록을 직접 전달해 확인할 수 있다.

## 9. PATH — 최단 경로와 동률 처리

**근거: Subject.txt 4장 `PATH` / 평가 1-4·2-4·3-3**

이 단계는 다음 세 조각을 순서대로 완성한다. 최단 거리만 구한 상태를 PATH 전체 완료로 표시하지 않는다.

### 9-1. 이웃 관계와 최단 거리

- [ ] 부모 연결을 무방향 간선으로 취급해 부모·자식 양쪽으로 이동할 수 있게 한다.
- [ ] 두 입력 커밋의 존재 여부를 먼저 구분한다.
- [ ] 간선 수를 기준으로 최소 거리를 찾는다. BFS 등 선택한 알고리즘이 이 기준에 맞는지 확인한다.
- [ ] 방문 기록으로 같은 연결을 계속 왕복하거나 불필요하게 반복 탐색하지 않도록 한다.

### 9-2. 실제 경로와 경로 없음

- [ ] 시작 커밋부터 도착 커밋까지의 실제 커밋 나열을 복원한다.
- [ ] 두 커밋이 존재하지만 연결되지 않았으면 `No path`를 출력할 수 있게 한다.
- [ ] 같은 커밋에서 자신으로 가는 경우는 간선 수 0인 경로로 처리한다.

### 9-3. 최단 경로의 사전순 동률 처리

- [ ] 길이가 같은 최단 경로가 여러 개이면 `hash1->hash2->...` 형태로 만든 **전체 문자열**의 사전순이 가장 작은 경로를 선택한다.
- [ ] ID를 숫자로 비교하거나 자료구조 순회 순서에만 의존한 결과가 아닌지 확인한다.
- [ ] 동률 처리를 위해 정렬이 필요하더라도 표준 정렬 API를 사용하지 않는다.

**완료 확인**

- [ ] 직접 부모·자식 관계에서는 양방향 모두 길이 1의 경로를 찾는다.
- [ ] 서로 다른 가지의 커밋 사이에서 공통 조상을 거치는 경로를 찾는다.
- [ ] 길이가 서로 다른 후보가 있으면 사전순보다 최단 길이를 우선한다.
- [ ] 길이가 같은 후보가 있으면 전체 경로 문자열 기준의 결과가 맞는다. 검증 자료의 입력·연결 나열 순서를 바꿔도 같은 결과가 나온다.
- [ ] 존재하지 않는 ID의 에러와, 존재하는 두 커밋 사이의 `No path`가 구분된다.

## 11. CLI 파싱·명령 연결·REPL

**근거: Subject.txt 2장·4장 「CLI 공통 규칙」·명령어 기능 요구 / 평가 1-1~1-6**

### 11-1. 입력 해석

- [ ] 명령어는 대소문자를 구분하지 않는다. 이 과정에서 메시지·작성자 등 인자 원문을 일괄 소문자로 바꾸지 않는다.
- [ ] 따옴표로 감싼 사용자명·커밋 메시지·검색 키워드를 공백이 포함된 하나의 인자로 읽는다.
- [ ] `SEARCH --author=<name>` 형식을 처리하며 공백이 있는 이름도 따옴표로 전달할 수 있다.
- [ ] `LOG --sort-by=date`와 `LOG --sort-by=author` 형식을 처리한다.
- [ ] 명령별 인자 수와 옵션 값을 검사하고 잘못된 입력에 일관된 최소 에러 메시지를 제공한다.
- [ ] 존재하지 않는 브랜치·커밋은 대상 이름 또는 ID를 포함해 구분한다. 명세의 예시는 `Invalid args`, `Unknown branch: <name>`, `Unknown commit: <hash>`다.
- [ ] D5의 아직 남은 빈 상태·초기화 전 입력 등의 처리 방식을 기록하고 CLI에 적용한다.

### 11-2. 명령 연결

- [ ] `INIT <user_name>` → 초기화 결과를 출력한다.
- [ ] `BRANCH <branch_name>` / `SWITCH <branch_name>` → 생성·전환 결과를 출력한다.
- [ ] `COMMIT <message>` → 생성 결과에 새 커밋 hash를 포함한다.
- [ ] `LOG` / `LOG --sort-by=date|author` → 기본·정렬 로그를 출력한다.
- [ ] `PATH <commit1> <commit2>` → 경로 또는 `No path`를 출력한다.
- [ ] `ANCESTORS <commit_hash>` → 조상 목록을 출력한다.
- [ ] `SEARCH <keyword>` / `SEARCH --author=<name>` → 검색 결과 커밋 목록을 출력한다.

### 11-3. 반복 실행

- [ ] 엔트리 포인트에서 REPL을 시작한다.
- [ ] `mini-git>` 프롬프트에서 입력 → 파싱 → 실행 → 출력이 반복된다.
- [ ] 같은 실행 중 이전 명령이 만든 커밋·브랜치·색인을 다음 명령에서 사용한다.
- [ ] `exit`와 `quit`로 종료한다.

**완료 확인**

- [ ] `init "Alice Kim"`, `CoMmIt "Add login feature"`, `SEARCH --author="Alice Kim"`으로 명령 대소문자·공백 인자·옵션 연결을 확인한다.
- [ ] 인자 누락·초과, 잘못된 정렬 값, 닫히지 않은 따옴표, 존재하지 않는 명령·브랜치·커밋에 일관된 안내가 나온다. 처리한 입력 오류 이후에는 다음 명령을 받을 수 있다.
- [ ] 종료 명령 두 가지를 각각 확인한다.

## 12. 전체 동작 확인과 제출 문서

**근거: Subject.txt 2장·4장·7장·8장 / 평가 항목 1**

### 실제 명령으로 확인할 흐름

아래 A·B·C는 실행 결과로 나온 실제 커밋 ID를 대신 부르는 이름이다.

| 순서 | 입력 / 동작 | 확인할 결과 |
| --- | --- | --- |
| 1 | `init "Alice"` | main·HEAD·현재 사용자 설정 |
| 2 | `commit "Initial commit"` | 부모 없는 A 생성 |
| 3 | `branch feature`, `switch feature` | feature 선택 |
| 4 | `commit "Add login feature"` | 부모 A인 B 생성 |
| 5 | `switch main`, `commit "Add payment feature"` | 부모 A인 C 생성, feature는 B 유지 |
| 6 | `log` | D3에 기록한 범위에서 부모 우선 출력. 저장소 전체라면 A는 B·C보다 먼저 출력 |
| 7 | `path B C` | 실제 B·C의 ID로 실행했을 때 B → A → C |
| 8 | `ancestors B` | A만 출력 |
| 9 | `search "login"` | B가 검색됨 |
| 10 | `search --author=Alice` | A·B·C가 검색됨 |
| 11 | 두 종류의 정렬 LOG | 기록한 날짜·작성자 정렬 규칙 준수 |
| 12 | `exit` 또는 `quit` | REPL 종료 |

- [ ] 위 흐름을 하나의 실행 세션에서 완료한다.

### 알고리즘에 직접 전달할 검증용 데이터

필수 명령만으로 만들기 어려운 그래프나 여러 작성자의 데이터는 내부 함수에 전달해 확인한다. 이를 만드는 새 CLI 명령을 추가하지 않는다. 시각 t0~t4는 크기를 비교할 수 있는 값이며 `t0 < t1 < t2 < t3 < t4`다.

| ID | parents | author | timestamp | message |
| --- | --- | --- | --- | --- |
| h0 | 없음 | Zoe | t1 | Initial commit |
| h1 | h0 | Alice | t3 | Add login feature |
| h2 | h0 | Bob | t2 | Fix login |
| h3 | h1, h2 | Alice | t4 | Ship login login |
| hx | 없음 | Evan | t0 | Separate history |

- [ ] `ANCESTORS h3`의 결과 집합이 h0·h1·h2이고 중복과 h3 자체가 없다.
- [ ] `PATH h0 h3`는 `h0->h1->h3`와 `h0->h2->h3` 중 사전순이 작은 첫 경로를 선택한다.
- [ ] `PATH h0 hx`는 `No path`, `PATH h0 h0`는 간선 수 0의 경로다.
- [ ] 기본 LOG는 h0를 h1·h2보다 먼저, h1·h2를 h3보다 먼저 출력한다. hx에는 다른 커밋과의 선후 제약이 없다.
- [ ] 키워드 `login`에는 h1·h2·h3이 각각 한 번, 작성자 `Alice`에는 h1·h3이 나온다.
- [ ] 날짜·작성자 순서가 서로 다른 목록에서 두 정렬 기준이 실제로 구별된다.

### 구조·제약·실행 문서

- [ ] 탐색·정렬·인덱싱이 독립된 함수 또는 클래스로 분리되어 있다.
- [ ] 주요 함수·클래스에 주석 또는 docstring을 작성했고, 역할·입출력·중요한 처리 규칙을 설명한다.
- [ ] 전체 코드에서 그래프 전용 라이브러리와 금지된 정렬 API를 사용하지 않았는지 확인한다.
- [ ] 엔트리 포인트 1개와 `README.md`를 제출할 수 있다. 엔트리 포인트가 하나라는 조건은 모든 코드를 한 파일에 넣으라는 뜻이 아니다.
- [ ] README에 Python 버전, 실제 실행 방법, 명령 사용 예시와 결정한 동작을 적어 프로그램을 실행할 수 있게 한다.
- [ ] README에 적은 명령으로 실행해 확인한다. 명세의 실행 예시는 `python main.py`다.
- [ ] 위 확인 중 남은 실패가 없고 D1~D5 중 구현에 영향을 주는 미정 사항이 남아 있지 않다.
